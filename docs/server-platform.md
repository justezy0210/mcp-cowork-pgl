# 서버 관리 웹

현재 프런트엔드는 React·Vite·shadcn/ui를 사용한다. 관리자 화면은 새 계정 승인,
사용자 권한, 서버 설정, 변경 이력 탭으로 구분한다. 모바일에서는 메뉴 버튼으로
같은 화면에 접근한다. 개발·빌드 절차는 [프런트엔드 안내](../frontend/README.md)를 따른다.

2026-09-28: 기존 `/web/`를 Google 로그인 기반 서버 관리 화면으로 확장했다.
종자·샘플·재고·데이터 관리는 이번 운영 화면의 메뉴에 포함하지 않는다.
실제 예약 원장·사용자 권한·SSH 연결 프로그램을 사용하며, 웹에서 계산 명령을 실행하거나 취소하지 않는다.
실제 허브에 적용했고 `ezy` 웹 관리자·허용 서버 네 대·스키마 5와 익명 관리 API 차단을 확인했다.
적용 전후 기존 `RUNNING` 작업 2개가 유지됐고 적용 직후 실행기 보고 지연은 최대 0.6초였다.

## 접속

2026-09-29부터 [공개 웹](https://mcp-cowork-pgl.web.app)에 접속한다. 브라우저 PC의 SSH 터널은 필요 없다.
Firebase Hosting → Cloud Functions → 제한된 SSH 중계 → 내부 허브로 연결한다.
[배포·비용 설정](firebase-hosting.md)을 참고한다.

관리자가 내부 허브 화면을 직접 점검할 때는 아래 SSH 연결과 `http://localhost:18080/web/`도 사용할 수 있다.

```sh
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:192.168.10.41:8080 \
  -p 2244 ezy@203.255.11.226
```

Google로 로그인한다. 초기 웹 관리자는 사용자 승인에 따라 `ezy`로 지정한다.
Google 로그인은 같은 탭에서 새로고침해도 유지된다. 로그아웃하거나 탭을 닫으면 세션이 해제된다.
메모리 방식으로 로그인한 기존 페이지는 이번 변경을 처음 불러온 뒤 한 번 다시 로그인해야 한다.
공개 웹과 localhost 화면은 주소가 다르므로 각각 로그인한다.

## 사용자 화면

| 메뉴 | 실제 동작 |
| --- | --- |
| 서버 현황 | 가로형 서버 카드를 위아래로 표시. 본인에게 허용된 서버의 CPU·메모리 예약량/예산, GPU 예약 개수, 실행·준비·대기 건수를 요약 |
| 서버 상세 | 서버 카드의 ‘작업 보기’로 이동. 해당 서버의 상세 자원·GPU별 예약 상태·진행 작업·대기 예약 표시 |
| 내 작업 | ‘전체’ 또는 허용 서버 버튼으로 본인 작업을 선택해 20개씩 조회. ‘완료된 작업 포함’을 체크하면 완료·실패·취소 내역도 표시. 상태·대기 이유·신청 자원·순번 표시 |
| 최초 계정 등록 | 첫 Google 로그인 시 계정 이름·UID·GID·Discord 웹훅 URL을 필수 입력. 관리자 승인 시 허용 서버 지정 |
| 작업할 컨테이너 | 메인 연결 프로그램·대상 서버 선택, SSH 접속 명령 한 줄로 컨테이너 연결 요청 |
| 개인 토큰 | 기존 발급·다운로드·목록·개별 폐기. 이름을 비우면 `사용자ID-MCP` 사용 |
| 메인 프로그램 설치 | 본인 UID/GID·허용 서버·Discord 상태, 단계별 설치·자동 등록·연결 검사, Codex/Claude 선택·명령 복사, SSH 추가·첫 작업·재시작·오류 대응 |

현황은 조회 중인 페이지가 보일 때 20초마다 갱신한다. 관리자 편집 중에는 자동 갱신하지 않는다.
마지막 조회 시각을 표시하며 조회 실패 시 해당 현황을 비우고 오류를 표시한다.
페이지 새로고침은 자원을 예약하거나 작업을 제출하지 않는다.
내 작업의 서버 필터는 배정된 서버를 기준으로 하며, 아직 배정되지 않은 작업은 신청한 후보 서버에 포함한다.
서버 버튼을 바꾸면 첫 페이지로 돌아가고 선택한 목록 안에서 순번을 다시 센다. 완료 내역 포함 설정은 유지한다.
선택은 자동 갱신과 메뉴 이동 시 유지하며, 선택한 서버의 권한이 회수되면 전체 목록으로 전환한다.
공통 소개와 카드 밖의 큰 제목 영역을 생략하고, 모든 메뉴의 첫 카드를 사이드바 상단에 맞춘다.
페이지 제목과 필요한 안내는 카드 안에, 마지막 조회 시각과 새로고침은 각 페이지 아래에 표시한다.
서버 상세의 목록으로 돌아가는 링크도 첫 카드 안에 표시한다.

서버 카드의 **작업 보기**를 누르면 서버별 상세 페이지(`/web/#servers/226` 등)로 이동해
같은 서버를 사용하는 사람들의 작업을 확인할 수 있다. **서버 목록** 링크로 돌아갈 수 있으며
브라우저 뒤로 가기·앞으로 가기와 상세 주소에서 새로고침을 지원한다.
첫 서버 목록에서는 요약만 조회하고, 작업 내역은 해당 상세 페이지 또는 **내 작업** 메뉴에서 조회한다.
직접 상세 주소를 입력해도 서버 권한을 확인하며, 허용되지 않은 서버의 정보는 표시하지 않는다.
작업 이름·사용자·상태·신청 CPU/메모리/GPU·접수/시작 시각을 표시한다.
허브에 등록된 작업만 표시하며, 허브를 거치지 않은 프로세스는 포함하지 않는다.

- **진행·예약 중:** `DISPATCHING`, `RUNNING`, `UNKNOWN`. 상태 확인이 필요한 작업도 기존 자원 예약을 유지한다.
- **대기 예약:** `QUEUED`. 아직 서버와 자원을 확보하지 않은 작업이며 신청한 실행환경의 서버에 표시한다. 여러 서버를 후보로 신청한 경우 각 후보 서버에서 보일 수 있고, 실제 배정 후에는 해당 서버에만 나타난다. 같은 서버의 환경을 여러 개 신청해도 중복 표시하지 않는다.

두 목록은 접수 순으로 20개씩 조회한다. 대기 목록 순서는 실행 순서 보장이 아니며 실행 가능한 작업부터 배정한다.
각 목록에 순번을 표시하고 페이지가 바뀌어도 이어서 센다. ‘내 작업’에서 종료된 작업의 순번은 비워 두며,
완료 내역 표시 여부와 관계없이 미완료 작업에만 같은 정렬 기준으로 연속 번호를 부여한다.
완료 내역 체크를 바꾸면 첫 페이지로 돌아간다. 순번은 현재 목록의 표시 번호이며 작업 ID나 실행 우선순위가 아니다.
완료 내역을 포함해도 순번이 있는 미완료 작업을 모두 먼저 표시하고, 종료된 작업을 그 뒤에 표시한다.
각 그룹 안에서는 최근 접수 순을 유지하며, 이 정렬은 페이지를 나누기 전에 적용한다.
선택한 서버와 페이지는 자동 갱신 때 유지하고, 대기 건수가 줄어 마지막 페이지가 사라지면 페이지 번호를 보정한다.
다른 사용자의 명령·인자·경로·로그·실행기 정보는 공유 목록에서 제공하지 않는다.
서버 조회 권한은 웹 관리자 여부와 관계없이 해당 서버 사용 권한을 확인한다.

CPU·메모리는 **신청량에 따른 예약 정보**다. 실제 프로세스 사용량이 아니다.
‘최근 실행기 보고 없음’은 관측 결과이며 SSH 연결 실패나 서버 전원 꺼짐을 뜻하지 않는다.
본인에게 허용되지 않은 서버의 예약·자원 상세는 공개하지 않는다.

별도의 서버 사용 신청 메뉴는 없다. 최초 계정 등록은 관리자 승인 대기 상태로 저장한다.
관리자가 계정·UID/GID·Discord 채널을 확인하고 허용 서버를 선택하면 함께 적용한다.
기존 계정은 재등록하지 않는다. 승인만으로 Docker 컨테이너나 SSH 키가 생성되지 않는다.
승인 후 메인 프로그램을 설치하고 **작업할 컨테이너**에서 다른 서버의 컨테이너를 연결한다.
`ssh -p 11010 alice@203.255.11.229`처럼 접속 명령을 입력하면 주소·포트·계정을 분리해 확인한다.
명령은 실행하지 않고 데이터로 해석한다. 추가 SSH 옵션이나 원격 명령은 거절한다.
설치 기준 경로는 메인 등록에서 가져오고, 실제 프로젝트 경로는 매 작업에서 지정한다.
메인 연결 프로그램이 꺼져 있으면 요청은 저장되어 다시 연결될 때 처리된다.
SSH 등록 결과의 `REGISTERED`는 요청 처리 완료이며, 실행환경은 등록 검사를 통과하면 `READY`가 된다. 컨테이너별 추가 승인은 없다.
SSH 개인키·비밀번호를 웹으로 전달하지 않는다.

기존 `PENDING_APPROVAL` 컨테이너는 허브 시작 시 활성 계정·허용 서버·UID/GID·CPU·메모리·GPU
검사를 다시 통과한 경우에만 자동 전환한다. 환경 ID와 실행기 설정은 유지된다.
자동 전환은 소유자 계정에 `environment.auto_register` 이력으로 기록한다.
검사에 실패한 항목과 `UNAVAILABLE` 환경은 그대로 두며, 등록 시 선택한 물리 서버를 별도로 증명하지는 않는다.

## 표시 언어

상단 오른쪽에서 한국어·English를 선택한다. 로그인 전·가입·일반 사용자·관리자 화면에 모두 적용하며
기본값은 한국어다. 선택은 브라우저에 저장하고 새로고침·로그아웃 후에도 유지한다.
`?lang=en` 또는 `?lang=ko`가 있으면 저장된 선택보다 우선한다. 예: `/?lang=en#guide`.
언어 전환은 화면만 갱신하므로 로그인, 입력 중인 폼, 발급 직후 토큰, SSH 확인 결과가 유지된다.
작업명·계정·경로 등 사용자 데이터와 실행 명령은 번역하지 않는다. 날짜·숫자는 선택한 언어로 표시한다.
웹 설치 안내와 에이전트에 보낼 첫 작업 예문도 영어를 지원한다. 연결된 상세 문서는 한국어임을 표시한다.
번역은 `frontend/src/lib/translations/en.ts`에서 관리하고 메시지와 보간 변수 누락을 검사한다.

## 관리자 화면

- **새 계정 승인:** Google 계정·계정 이름·UID/GID·Discord 채널을 확인하고 허용 서버를 선택한다. 계정·Google 연결·서버 권한·알림 목적지·변경 이력은 한 DB 트랜잭션으로 저장한다. 승인 전에는 토큰 발급이나 서버 접근을 허용하지 않는다. 거절하면 사용자가 정보를 수정해 재제출할 수 있다.
- **사용자별 허용 서버:** 체크박스로 선택해 저장한다. 조회 이후 권한이 바뀌면 저장을 거절해 새로고침하도록 한다.
- **예약 예산·배정 중지:** 등록된 서버의 CPU·메모리 예산과 새 배정 허용 여부를 변경한다. 예약 중인 CPU·메모리보다 작은 예산은 거절한다. GPU 목록 변경과 물리 서버 최초 등록은 기존 관리자 등록 도구를 사용한다.
- **변경 이력:** 신청·검토·권한·예산·계정 연결·기존 환경 자동 등록 기록과 변경 전후 값을 조회한다. 토큰·Webhook·SSH 비밀정보는 기록하지 않는다.

권한 회수와 새 배정 중지는 이미 실행 중인 계산을 취소하거나 예약을 반환하지 않는다.
기존 작업의 실행기 보고와 실제 종료 처리는 계속된다.
관리자가 한 연구실 Discord 서버에 사용자별 비공개 채널을 만들고 해당 사용자에게 보기 권한을 준다.
사용자는 처음 계정 등록 때 본인 채널 웹훅을 입력한다. 이후 변경은
**관리자 → 사용자별 서버 권한·Discord 채널**에서 처리한다.
일반 사용자는 **Discord 알림**에서 본인 채널의 연결 상태만 확인한다.
허브의 Discord 서버 허용 목록에 속하는지 확인하며, 다른 사용자에게 연결된 채널은 거절한다.
기본 서버는 `HUB_DISCORD_GUILD_ID`, 추가 서버는 `HUB_DISCORD_ADDITIONAL_GUILD_IDS`에 쉼표로 구분해 설정한다.
기존 서버를 남겨 두면 그 서버에 연결된 이전 작업의 알림도 유지된다.
정상 웹훅이지만 허용되지 않은 서버라면 `DESTINATION_GUILD_NOT_ALLOWED`를 반환하고 웹에서 원인을 구분해 안내한다.
작업 알림은 제출자의 채널만 사용한다. 채널 미설정 시 작업 제출이 거절되며 공용 채널로 대체하지 않는다.
채널 변경은 새 제출부터 적용하고 이미 제출한 작업의 알림 경로는 유지한다.
설치·배포 등 허브 작업 밖에서 실행하는 운영 명령의 알림 래퍼는 별도 설정을 사용한다.

## 인증·API·저장

`GET /v1/web/onboarding`은 Google 인증 후 본인의 등록 상태를 조회한다.
`POST /v1/web/onboarding`은 `{account_name, uid, gid, webhook_url}`을 받으며 네 항목 모두 필수다.
관리자는 `GET /v1/web/admin/enrollments`로 대기 목록을 조회하고
`POST /v1/web/admin/enrollments/{id}/review`에 결정과 허용 서버를 전달한다.
`POST /v1/web/ssh/parse`는 SSH 명령을 해석한다. `POST /v1/web/containers`는
`{connector_id, node_id, ssh_command, request_key}`로 SSH 연결 검사·자동 등록 절차를 사용한다.
기존 서버 사용 신청·수동 계정 연결 API와 기록은 호환성을 위해 보존하지만 새 화면에서는 사용하지 않는다.

`/v1/web/profile`은 허브 사용자·기준 UID/GID·허용 서버·알림 연결 상태·웹 관리자 여부를 반환한다.
`GET /v1/web/notifications`는 본인의 연결 여부·채널 ID만 반환한다.
`POST /v1/web/admin/users/{user_id}/notifications`는 관리자만 사용할 수 있고,
`{ "webhook_url": "…" }`를 받아 지정한 사용자에게 연결한다.
관리 변경 이력에는 관리자·대상 사용자·이전/새 채널 ID만 기록한다.
웹훅 URL·비밀 참조는 응답·로그·브라우저 저장소에 남기지 않는다.
허브의 `HUB_DISCORD_GUILD_ID` 설정이 필요하며, 새 웹훅은 데이터 볼륨의 `discord-users.json`에
권한 `0600`으로 원자적으로 저장한다. 허브 재시작 후에도 유지되며 DB와 함께 비공개 백업 대상이다.
기존 환경변수와 관리자 비밀 파일에 등록된 채널은 보존한다. 웹훅 등록에 허브 재시작은 필요 없다.
`/v1/web/servers`, `/jobs`, `/environments`, `/connectors`, `/registrations`, `/access-requests`는 본인 범위에서 동작한다.
`/v1/web/servers/{node_id}/jobs?group=active|queued&page=1&page_size=20`은 허용된 서버의 공유 작업 요약을 반환한다.
`/v1/web/jobs`는 기본으로 종료된 작업을 제외한다. `include_completed=true`로 전체 내역을 조회할 수 있고,
실행 중 → 다른 미완료 작업 → 종료 작업 순으로 정렬하며 각 그룹은 최근 접수 순이다.
서버별 공유 목록도 실행 중인 작업을 먼저 표시한다. 대기 예약 목록은 기존 접수 순을 유지한다.
`number`는 미완료 작업의 표시 순번이며 종료된 작업은 `null`이다. 필터와 순번은 DB 조회 시 적용해 페이지 사이에서도 일관되게 표시한다.
`node_id`를 지정하면 해당 서버의 본인 작업만 조회하며, 서버 사용 권한을 검사한 뒤 페이지를 나누기 전에 필터링한다.
`/v1/web/admin/` 아래 신청 검토·사용자·권한·서버·이전 환경 승인 호환·감사 API는 별도로 관리자 권한을 검사한다.
모든 웹 API는 검증된 Firebase Google ID 토큰을 요구한다. 개인 MCP 토큰이나 관리자 Bearer 토큰으로 웹 관리자 권한을 얻을 수 없다.

비공개 웹 설정의 `admin_users`에는 웹 관리자로 허용한 **허브 사용자 ID**를 넣는다.
관리자도 허브의 `user` 역할을 유지하므로 기존 개인 계산·MCP 인증에 영향을 주지 않는다.
이 설정은 관리자 화면에서 자기 승격할 수 없으며 호스트의 비공개 설정에서 관리한다.
추가 사용자의 Firebase 계정 연결은 `web_accounts`에 저장하므로 계정을 추가할 때마다 허브를 재시작하지 않는다.
기존 비공개 `users` 매핑은 계속 사용한다. 관리자 설정·계정 매핑은 공개 웹 구성과 Hosting 출력에서 제외한다.

현재 스키마 6은 `web_enrollments`와 승인 대기 계정 이름·UID의 중복 방지 인덱스를 추가한다.
기존 사용자·토큰·환경·작업·예약을 다시 작성하지 않는다. PostgreSQL 스키마 4·5에서 6으로 한 트랜잭션으로 확장하며,
SQLite도 기존 데이터를 보존해 확장한다. SQLite → PostgreSQL 이전 도구는 현재 스키마의 원본을 사용한다.
스키마 6 적용 후 구버전 허브 이미지로 바로 되돌리면 스키마 검사에서 거절될 수 있으므로
운영 중에 오래된 DB 백업으로 덮어쓰지 않는다. 현재 DB를 보존한 복구 절차를 사용한다.
