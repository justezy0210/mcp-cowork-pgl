# Worker 연결 계약 (구현 예정)

> 실행 방식 정정 (2026-09-18): 사용자 측 실행 스크립트가 자원을 신청하고 **해당 작업의 예약 허가**를
> 기다렸다가 명령을 실행한다. 현재 컨테이너에서는 로컬 실행하며 다른 컨테이너에는 사용자 측 SSH로
> 접속한다. 허브는 Docker 관리나 SSH를 통한 직접 실행·중지를 하지 않는다. SSH 인증 준비와 허브의
> 사용자별 허용 서버 정책을 함께 적용한다. 에이전트가 아닌 스크립트가 대기·실행·종료 보고를 담당한다.
> 이 정정은 아래 기존 설계의 호스트 Worker·Docker 런타임 검증·노드 전체 Worker 토큰 배치를 대체한다.
> 본인 환경·작업 범위의 로컬 실행 API와 스크립트를 구현하고 임시 허브에서 실제 프로세스로 검증했다.
> 운영 허브 배포와 226의 실제 실행·대기 전환·Discord 알림 검증을 완료했다. 아래 호스트 Worker 계약은 이전 설계 기록이다. 현재 단계는 [현재 컨테이너 연결 안내](worker-226-setup.md)를 따른다.

이 문서는 허브 API를 사용하는 Worker가 보장해야 할 사항이다. 현재 배포 가능한 Worker는 없다.
허브 API만 연결하고 실제 프로세스 제어·중복 방지 없이 운영해서는 안 된다.

수동 `cowork-run`과 에이전트 MCP는 같은 허브 작업 형식으로 제출한다. Worker는 제출 경로와 관계없이
동일한 실행·중복 방지·완료 보고·취소 절차를 적용한다. 사용자 CLI는 계산을 별도로 로컬 실행하지 않는다.

## 신원과 등록 확인

- 물리 서버 하나에 노드 ID 하나를 등록하고 해당 서버 전용 Worker 토큰을 배치한다.
  같은 서버를 여러 노드 이름으로 등록해 예산을 중복 계산하지 않는다.
- 사용자 SSH 경로는 사용자 측 설정으로 해석한다. 허브가 SSH 개인 키나 비밀번호를 보관하지 않는다.
- 사용자는 `/v1/environments`에서 받은 검증값을 실제 접속한 컨테이너에서 전달한다.
  Worker는 호스트 Docker 런타임을 이용해 **실제 컨테이너 ID, 실행 UID/GID, 접속 컨텍스트**를 확인한다.
  공유 NFS 파일에 검증값이 있다는 사실이나 컨테이너가 주장하는 호스트 이름만으로 확인하지 않는다.
- Worker의 `/verify` 보고는 신뢰된 확인 결과다. 외부 사용자가 입력한 컨테이너 ID·UID를 그대로 전달하는 중계기를 만들지 않는다.
- [UID/GID 운영 규칙](../plans/container-job-orchestration.md#uidgid-운영-규칙)에 따라 실제 실행 UID·기본 GID를 보고한다. 허브 코드에 기준값 대조를 구현했으며 운영 배포와 사용자 기준값 설정이 필요하다. 실행 직전에도 등록된 실행 신원과 작업 경로 접근 권한을 확인한다.
- 유효 컨테이너 예산과 물리 GPU UUID 목록을 보고한다. 컨테이너 내부 GPU 인덱스를 물리 ID로 사용하지 않는다.
- 검증된 컨테이너 ID는 불변이다. 컨테이너 교체는 새 등록을 만들어 확인한다.

## Heartbeat와 배정

기본 heartbeat 간격은 10초 이하로 하고, 검증 완료된 환경 전체를 보낸다.
누락·컨테이너 ID 변경·GPU 접근 집합 변경은 해당 환경을 `UNAVAILABLE`로 만든다.
서버 전체의 마지막 보고가 45초보다 오래되면 허브는 기존 배정을 `UNKNOWN`으로 유지한다.

배정 목록은 **실행해야 할 새 명령의 일회성 큐가 아니다.** 현재 미종료 예약의 반복 가능한 스냅샷이다.
`execution_id`별 Worker 로컬 영속 원장과 대조한다. 같은 배정을 여러 번 받아도 한 번만 실행한다.
CPU/RAM 예약량, 실제 argv, 작업 경로, 컨테이너 ID/UID/GID, GPU UUID 집합을 그대로 적용한다.
실행 직전에 컨테이너와 GPU 접근 상태를 다시 확인한다.

수동 CLI 연결 단계에서 작업별 `workdir`을 배정 정보에 추가한다. 지정되면 그 경로를 사용하고,
기존 요청처럼 생략되면 등록 환경의 작업 경로를 사용한다. 대상 컨테이너 안에서 경로·실행 파일·입력 접근을
확인하며 다른 경로로 임의 변경하거나 파일을 자동 복사하지 않는다. 제출 셸의 conda 활성화·alias·전체 환경변수는
자동 전달되는 것이 아니므로 등록 환경이나 명시적인 실행 스크립트로 준비해야 한다.

`GET /v1/worker/assignments?since=<revision>&wait_seconds=25`로 변경을 기다릴 수 있다.
heartbeat 전송과 배정 대기는 독립적으로 진행한다. 여러 페이지가 있으면 `after=<마지막 seq>`로 이어 읽고,
변경 이후에는 다시 첫 페이지부터 대조한다. `revision`은 허브 재시작 시 바뀐다.

허브가 새 `DISPATCHING`을 만든 뒤 실행 확인 전에 단절되면 실제 실행 여부를 알 수 없다.
Worker 로컬 기록이 사라진 경우 실행 중인 프로세스·컨테이너를 대조하기 전에는 같은 작업을 다시 시작하지 않는다.
`UNKNOWN`을 처음 받은 새 Worker가 그 사실만으로 명령을 실행해서는 안 된다.

## 실행 및 보고

`argv`는 인자 배열이다. 문자열로 합쳐 셸에 전달하지 않는다. 셸 기능이 필요하면 제출자가
`["bash", "/work/script.sh"]`처럼 명시적으로 요청한다. 스크립트 파일 내용 자체는 허브가 보관하지 않으므로
재현성이 필요하면 변경 불가능한 스크립트 사본을 사용한다.

작업 단위의 프로세스 그룹과 필요한 하위 프로세스를 추적한다. CPU·메모리는 강제 cgroup 제한을 추가하지 않고
예약량으로 관리하며, 실제 threads 인자는 사용자가 승인한 argv에 들어 있어야 한다.
GPU 장치 선택은 보고된 UUID를 실제 실행 환경에 맞게 적용하고 시험한다. 환경변수만으로 강제 격리를 보장하지 않는다.

실제 시작과 종료를 로컬에 영속 기록한 뒤 이벤트를 전송한다.

```json
{
  "event_id": "STABLE_EVENT_ID",
  "execution_id": "ASSIGNED_EXECUTION_ID",
  "kind": "succeeded",
  "occurred_at": 1800000000.0,
  "exit_code": 0,
  "log_path": "/work/logs/job.log",
  "result_path": "/work/results/job"
}
```

- `started`: 실제 프로세스 시작 확인. `exit_code` 없음.
- `succeeded`: 작업과 필요한 자식의 정상 종료 및 정리 완료. `exit_code=0`.
- `failed`: 비정상 종료·정리 확인. 종료코드가 있으면 보고하며 0은 허용하지 않음.
- `cancelled`: 실제 작업 중단·정리와 같은 실행 ID의 지연 재실행 차단까지 완료.
- `not_started`: 실행하지 않았고 앞으로도 같은 실행 ID를 실행하지 않음이 확정됨.

동일 이벤트의 재전송에는 **같은 event_id·시각·본문**을 쓴다. 응답을 받기 전에는 이벤트를 삭제하지 않는다.
동일 ID에 다른 본문을 보내면 충돌이다. 시작 보고도 종료 보고와 동일하게 저장하고 재시도한다.
재연결 후 현재 실행 상태를 대조해 새로 보고하는 이벤트에는 새 ID를 사용한다.
서버 간 시간은 동기화한다. 시작보다 이른 종료 시각과 허브보다 5분 이상 미래의 보고는 거절된다.

## 취소 경합

`cancel_requested=true`를 보면 Worker는 해당 실행 ID에 대해 영속 취소 기록을 먼저 만든다.
시작·취소 판정을 직렬화하고, 이후 도착하는 오래된 시작 요청은 Worker 재시작 후에도 거절한다.
실행 중이면 프로세스 트리를 종료하고 정리한다. 실제 실행과 지연 실행 가능성이 모두 제거된 뒤에만
`cancelled` 또는 `not_started`를 보고한다. 허브는 그때 예약을 반환한다.

Worker 토큰이 있다는 이유로 API 호출만 해서 자원을 반환하지 않는다. 이벤트는 실제 관찰 결과여야 한다.
실행 여부가 불명확하면 상태를 대조하고 예약을 유지한다. 시간 초과로 성공·실패를 추정하지 않는다.

## 알림 책임

허브가 시작·종료 이벤트로 Discord 알림을 만든다. Worker·에이전트·수동 CLI는 같은 작업에 별도 Discord 완료 래퍼를
추가하지 않는다. 기존 사용자 스크립트에 포함된 알림 호출은 연결 시험에서 확인하고 사용자와 조정한다.
