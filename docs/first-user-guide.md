# 처음 사용하는 연구실 구성원 안내

2026-10-02 구현 기준이다. **Google 로그인 → 계정 등록·승인 → 설치 화면에서 명령 실행·토큰 준비 → 컨테이너 자동 등록 → 첫 작업** 순서로 진행한다.
소스는 [GitHub 저장소](https://github.com/justezy0210/mcp-cowork-pgl)에서 받는다.
별도의 서버 사용 신청 없이 관리자가 계정을 승인하면서 허용 서버를 지정한다.
[서버 관리 웹](server-platform.md)의 현재 접속 방법과 [웹 토큰 안내](web-tokens.md)를 따른다.
[웹 플랫폼](https://mcp-cowork-pgl.web.app)에서 Google로 로그인한다. 웹 접속을 위한 PC의 SSH 터널은 필요 없다.
웹의 **메인 프로그램 설치**에서 클라이언트·메인 서버·설치 폴더를 입력하고
본인 값이 반영된 설치 명령이 바로 표시된다. 별도의 안내 생성 버튼은 없다.
계정 이름으로 제안하는 경로는 실제 본인 소유 공유 경로인지 확인한다. 허브 주소는 필요할 때만
별도 설정을 펼쳐 변경한다. 입력값은 서버에 저장하지 않으며 로그아웃하면 지운다.
설치 명령은 단일 설치 프로그램을 다운로드해 실행한다. 같은 설치 화면에서 **토큰 발급 → 토큰 복사** 후
설치 프로그램의 숨김 입력란에 붙여 넣는다. 채팅이나 명령 인자에 넣지 않는다.
설치 안내 폼에는 토큰을 입력하지 않는다. 입력값을 바꾸면 명령이 즉시 갱신된다.
프로젝트 폴더는 설치할 때 지정하지 않는다. MCP는 작업마다 프로젝트의 절대 경로를 전달하고,
수동 CLI는 명령을 실행한 현재 폴더를 사용한다. 프로젝트를 옮겨도 재설치·재등록하지 않는다.
메인 컨테이너는 평소 에이전트를 켜거나 작업을 제출하는 개인 컨테이너를 뜻한다.
에이전트가 있는 메인에 설치하고 다른 컨테이너는 SSH로 추가한다. 대상마다 에이전트와 MCP를 설치하지 않는다.
이미 설치했다면 재설치·재등록 대신 4단계의 연결 검사부터 진행한다.

## 간편 설치 (권장)

관리자가 연구실 Discord 서버에 사용자별 비공개 채널을 만들고 본인에게 웹훅 URL을 전달한다.
사용자는 최초 계정 등록 시 URL을 입력하며, 계정 승인과 함께 알림 채널이 연결된다.
사용자는 초대받은 채널에서 알림을 받으며 웹의 **Discord 알림**에서 연결 상태를 확인한다.
작업 소유자의 채널로만 알림을 보내며, 미설정 사용자의 알림을 공용 채널로 대신 보내지 않는다.
채널 변경은 새 작업부터 적용되고 이미 제출한 작업은 기존 채널을 유지한다.
입력한 웹훅 URL은 저장 후 다시 표시하지 않는다. 이후 채널 변경은 관리자에게 요청한다.

1. **메인 프로그램 설치**에서 만든 명령을 메인 컨테이너 터미널에 한 번 붙여 넣는다.
2. 프로그램이 토큰을 요청하면 같은 설치 화면에서 **토큰 발급 → 토큰 복사**를 누르고 터미널에 붙여 넣는다.
3. 설치 결과에서 환경 등록·Discord 준비 상태를 확인하고 에이전트를 다시 시작한다.

설치 프로그램이 UID/GID·서버 권한 확인, 비공개 토큰 저장, Python 가상환경·의존성 설치,
메인 환경 등록, Codex/Claude의 MCP 등록과 스킬 연결, 연결 프로그램 자동 시작 등록, 실제 MCP 연결 검사를 처리한다.
본인 계정으로 실행하면 기존 Supervisor의 서비스 등록 단계에서만 필요한 `sudo` 인증을 요청한다.
연결 프로그램은 본인 계정으로 실행된다. 설치 명령 전체에는 `sudo`를 붙이지 않는다.
Git이나 수동 토큰 파일 전송은 필요 없다. Linux·Python 3.12 이상·curl·선택한 에이전트는 준비돼 있어야 한다.
처음에는 인터넷으로 Python 의존성도 내려받는다. 기존 MCP·스킬·설정은 덮어쓰지 않는다.
기존 스킬 링크가 끊겼거나 `SKILL.md`를 읽을 수 없으면 프로그램 설치는 계속하지만
“스킬 자동 선택 준비 안 됨”과 확인할 경로를 안내한다. 해당 경로를 복구한 뒤 처음 설치 명령을 다시 실행한다.
Codex의 다른 지원 경로에 정상 스킬이 있으면 그것을 보존하며 중복 설치하지 않는다.
컨테이너는 허용 서버·UID/GID·자원 검사를 통과하면 자동으로 `READY`가 된다. 설치 프로그램은 계산을 제출하지 않는다.

토큰은 브라우저를 닫은 뒤에도 컨테이너의 프로그램이 본인 계정으로 허브를 이용하기 위한 인증 정보다.
처음 한 번만 입력하며 이후 설치·업데이트에서 저장된 토큰을 재사용한다. 명령문·브라우저 저장소에는 넣지 않는다.

같은 설치를 다시 실행하면 프로그램·토큰·환경 등록을 재사용한다. 설치 기록을 확인한 폴더는
수정본으로 교체하고 이전 소스를 정리한다. 설치 기록이 없거나 다른 소스에서 만든 폴더는 보존한다.
기존 MCP가 이미 등록돼 있다면 해당 등록을 유지하며 사용자가 에이전트에서 연결 대상을 확인한다.
`자동 시작 등록 완료`이면 컨테이너의 Supervisor 시작 시 연결 프로그램이 자동 실행된다.
기존 간편 설치는 웹의 ‘자동 시작·기존 설치 적용’ 명령으로 재설치 없이 자동 시작만 추가할 수 있다.
Supervisor가 없거나 관리자 인증이 불가능하면 `자동 시작 미설정`을 표시한다.
`SUPERVISOR_NOT_CONFIGURED`는 계정 승인 문제가 아니라 지원하는 자동 시작 구성이 없다는 뜻이다.
이 경우 `sudo` 재시도 대신 컨테이너 관리자에게 시작 방식에 맞는 등록을 요청하고,
완료 전에는 본인 계정으로 안내된 수동 시작 명령을 사용한다. 수동 시작은 컨테이너 재시작 후 자동 실행을 보장하지 않는다.

아래는 수동 설치가 필요할 때 참고하는 상세 절차다. 간편 설치가 완료됐다면 반복 실행하지 않는다.

### 기존 설치 업데이트

웹의 **메인 프로그램 설치 → 기존 설치 업데이트**를 선택하고 처음 설치한 폴더만 지정한다.
표시된 명령을 기존 메인 컨테이너에서 실행하면 저장된 서버·허브·토큰을 읽는다.
Codex/Claude 선택이나 새 토큰 발급·MCP 재등록은 필요 없다. 다운로드한 설치 파일이 있다면 다음과 같다.

```sh
python3 cowork-setup.pyz --root /10Gdata/본인계정/cowork --update
```

연결 프로그램은 수정본으로 재시작한다. 사용 중인 에이전트의 MCP는 다시 연결하거나 에이전트를 재시작한다.
기존 Cowork 스킬이 있는 Codex·Claude에는 새 `cowork-data-library` 스킬도 자동으로 추가한다.
기존 스킬과 MCP 등록은 유지하며, 사용자가 별도로 관리하던 스킬은 덮어쓰지 않는다.
환경 등록 전에 중단되어 `runner.json`이 없는 경우에는 **처음 설치 · 중단된 설치 다시 진행**을 선택한다.
서버 권한과 UID/GID는 업데이트 때도 확인한다. 최초 계정 승인만 필요하며 컨테이너별 추가 승인은 없다.

## 1. 최초 계정 등록과 승인

Google로 처음 로그인하면 **내 계정 등록**에서 아래 네 항목을 모두 입력한다.

| 항목 | 확인 방법·용도 |
| --- | --- |
| 서버에서 사용하는 유저 ID | 메인 컨테이너에서 `whoami`. 본인의 허브 계정 이름으로 사용 |
| 계정 UID | `id -u`. 작업 파일 소유자 확인 |
| 계정 GID | `id -g`. 공유 파일 그룹 권한 확인 |
| Discord 웹훅 URL | 연구실 서버의 본인 알림 채널 웹훅. 관리자가 만든 채널이라면 URL을 전달받음 |

동일 사용자의 UID/GID는 사용하는 모든 서버·컨테이너에서 일치해야 한다.
**다른 사람까지 같은 UID를 쓰는 규칙은 아니다.** GID는 연구실 그룹 정책에 따라 공유할 수 있다.
다른 사람의 계정 이름·UID·웹훅을 복사하지 않는다.

**계정 등록 요청**을 누르면 관리자 승인 대기가 된다. 관리자는 **새 계정 승인**에서 정보를 확인하고
허용 서버를 선택해 승인한다. 별도의 서버 사용 신청이나 Firebase 계정 식별자 전달은 필요 없다.

새 신청이 접수되면 관리자의 등록된 Discord 채널로 유저 ID, UID/GID와 승인 페이지 링크를 보낸다.
중복 제출은 알림을 추가하지 않으며, 일시적인 전송 실패나 허브 재시작 후에는 전송을 재시도한다.
관리자 채널이 아직 설정되지 않았다면 설정될 때까지 대기하고, 이미 검토가 끝난 신청은 보내지 않는다.
승인 전에는 개인 토큰 발급·설치·작업 제출을 사용할 수 없다.
승인 후 **승인 상태 확인**을 누르면 계정 화면으로 들어간다. 기존에 연결된 계정은 재등록하지 않는다.

**개인 토큰**에서 본인 토큰을 발급할 수 있다. 새 컨테이너는 등록 검사를 통과하면 추가 승인 없이 사용할 수 있다.
사용자는 허브 컨테이너에 로그인하거나 Docker 관리 권한을 받을 필요가 없다.

## 2. 메인 컨테이너에서 설치 준비

본인 계정으로 실행한다. `sudo`로 설치하지 않는다. Linux와 Python 3.12 이상이 필요하다.

```sh
id -u
id -g
python3 --version
curl --fail --max-time 5 http://192.168.10.41:8080/healthz
```

허브 주소는 관리자가 안내한 주소를 사용한다. 현재 연구실 내부망 주소는 위와 같다.
공개 웹 주소 `https://mcp-cowork-pgl.web.app`은 브라우저용이다. MCP·CLI의 `--hub-url`을
이 주소로 바꾸지 않는다. 메인과 SSH 대상 모두 내부 허브에 접근할 수 있어야 한다.
허브 정상 응답은 연결 확인이며 개인 인증이나 환경 등록 완료를 뜻하지 않는다.
Python이 3.12 미만이면 설치를 계속하지 말고 해당 컨테이너의 Python 3.12 이상 경로를 확인한다.

아래 `alice`, `226`, 경로는 예시다. **본인 경로와 실제 메인 서버 ID로 바꾼 뒤 같은 터미널에서 진행한다.**
`COWORK_ROOT`는 본인 소유 공유 디렉터리여야 한다. 메인과 SSH 대상에서 설치 경로·개인 설정·토큰·
작업 경로가 같은 절대 경로로 보이고, 설치에 사용한 기반 Python도 대상에서 실행 가능해야 한다.

```sh
export COWORK_ROOT=/10Gdata/alice/cowork
export COWORK_HUB_URL=http://192.168.10.41:8080
export COWORK_NODE=226
export COWORK_BIN="$COWORK_ROOT/client-0.1.0/venv/bin"
export COWORK_SOURCE="$COWORK_ROOT/source"

umask 077
mkdir -p "$COWORK_ROOT/state"
chmod 700 "$COWORK_ROOT/state"
```

**브라우저 PC**에서 웹의 개인 토큰을 다운로드한 뒤 SFTP 또는 `scp`로
**메인 컨테이너**의 `$COWORK_ROOT/state/user.token`에 전송한다.
아래는 PC 터미널에서 실행하는 예시다. 포트·계정·호스트·다운로드 위치·목적 경로를 실제 값으로 바꾼다.
컨테이너의 `$COWORK_ROOT` 변수는 PC 터미널에 없으므로 목적 경로를 직접 적는다.

```sh
scp -P 11019 ~/Downloads/user.token alice@203.255.11.226:/10Gdata/alice/cowork/state/user.token
```

기존 토큰 파일이 있다면 전송으로 덮어쓰기 전에 사용 중인지 확인한다.
이후 명령은 다시 **메인 컨테이너의 같은 터미널**에서 실행한다.
본인 소유 일반 파일이어야 하며 심볼릭 링크는 사용할 수 없다. 내용은 출력하지 않는다.

```sh
chmod 600 "$COWORK_ROOT/state/user.token"
stat -c '%U %a %n' "$COWORK_ROOT/state/user.token"
```

Git이 설치된 환경에서 소스를 본인 공유 경로로 내려받는다. 비공개 저장소라면 먼저 본인 GitHub 계정에
접근 권한을 받아야 한다. 아래 `source`는 새 디렉터리여야 한다.

```sh
git clone https://github.com/justezy0210/mcp-cowork-pgl.git "$COWORK_ROOT/source"
export COWORK_SOURCE="$COWORK_ROOT/source"
python3 "$COWORK_SOURCE/scripts/install_connector.py" \
  --prefix "$COWORK_ROOT/client-0.1.0"
```

`installed: true`가 성공 기준이다. 인터넷 연결이 없으면 관리자가 준비한 의존성 파일 디렉터리를
`--wheelhouse`로 지정하고 소스도 관리자가 파일로 제공해야 한다.
현재 버전별 GitHub Release 첨부 파일은 게시하지 않았다. 자세한 전제는 [설치 안내](connector-setup.md)를 참고한다.
각 단계에서 오류가 나면 중단하고 원인을 확인한다. 새 터미널을 열었다면 위 경로 설정 블록을 다시 실행한다.

## 3. 메인 환경 등록과 연결 프로그램 시작

```sh
"$COWORK_BIN/cowork-connector" configure \
  --hub-url "$COWORK_HUB_URL" \
  --token-file "$COWORK_ROOT/state/user.token" \
  --node "$COWORK_NODE" --workdir "$COWORK_ROOT" \
  --config "$COWORK_ROOT/state/connector.json"

"$COWORK_BIN/cowork-connector" start \
  --config "$COWORK_ROOT/state/connector.json"

"$COWORK_BIN/cowork-connector" status \
  --config "$COWORK_ROOT/state/connector.json"
```

메인 실행기 설정은 `$COWORK_ROOT/state/runner.json`에 자동으로 생성된다.
위 `configure --workdir`는 환경 등록에 필요한 경로이며 설치 폴더를 사용한다.
실제 계산 위치는 매 작업의 `spec.workdir`로 지정하므로 등록 경로 아래로 제한되지 않는다.
기존에 다른 경로로 등록했더라도 프로젝트 변경 때문에 이 설정을 바꾸지 않는다.
`configure`가 반환한 `environment_id`는 검사를 통과하면 바로 `READY`가 된다.
계정 승인 때 지정된 서버 권한과 UID/GID를 재사용하며 컨테이너별 추가 승인은 없다.
사용자 설치 때마다 허브를 재설치하지 않는다.

`status`의 `running: true`는 로컬 프로세스가 살아 있다는 뜻이다. 허브의
웹의 **작업할 컨테이너**에서 연결 프로그램 ‘연결됨’, 해당 환경 ‘사용 가능(READY)’까지 확인한다.
연결 프로그램은 SSH 등록 요청을 처리한다. 계산 작업의 대기·실행은 별도 작업 실행기가 담당한다.

## 4. 에이전트를 사용하는 경우 MCP 연결

수동 명령만 사용할 사람은 클라이언트 등록·스킬 설치를 건너뛰고 이 단계 마지막의 읽기 전용 연결 검사부터 실행한다.
Codex 또는 Claude Code가 설치된 **메인 컨테이너**에서 다음을 실행한다.

Codex 등록 명령은 다음과 같다.

```sh
codex mcp add cowork -- \
  "$COWORK_BIN/cowork-mcp" \
  --hub-url "$COWORK_HUB_URL" \
  --token-file "$COWORK_ROOT/state/user.token" \
  --runner-config "$COWORK_ROOT/state/runner.json"

codex mcp get cowork
```

Claude Code 등록 명령은 다음과 같다.

```sh
claude mcp add cowork -s user -- \
  "$COWORK_BIN/cowork-mcp" \
  --hub-url "$COWORK_HUB_URL" \
  --token-file "$COWORK_ROOT/state/user.token" \
  --runner-config "$COWORK_ROOT/state/runner.json"

claude mcp get cowork
```

허브 주소의 `:8080`은 REST API다. 이 주소를 원격 MCP 주소로 등록하는 대신 위 실행 명령을 등록한다.
그 밖의 MCP 클라이언트도 같은 `cowork-mcp` 실행 파일과 인자를 **stdio 서버**로 설정한다.
클라이언트별 설정 파일 형식은 다르므로 Codex·Claude Code 설정을 그대로 복사하지 않는다.

계산 요청 시 참고할 `cowork-jobs` 스킬도 설치한다.
새 Codex 설치는 [공식 사용자 스킬 경로](https://learn.chatgpt.com/docs/build-skills)인
`~/.agents/skills`를 사용한다. 기존 `~/.codex/skills`에서 이미 발견되는 스킬은 중복 설치하지 않는다.
기존 스킬이나 MCP 등록이 있으면 먼저 확인하고 덮어쓰지 않는다.
등록과 스킬 설치는 사용하는 클라이언트에 해당하는 명령만 실행한다.

```sh
mkdir -p "$HOME/.agents/skills"
ln -sT "$COWORK_SOURCE/skills/cowork-jobs" "$HOME/.agents/skills/cowork-jobs"
```

```sh
mkdir -p "$HOME/.claude/skills"
ln -sT "$COWORK_SOURCE/skills/cowork-jobs" "$HOME/.claude/skills/cowork-jobs"
```

링크 원본을 계속 사용하므로 내려받은 소스 디렉터리를 지우지 않는다.
에이전트를 다시 연결하고 다음과 같이 요청한다.

> cowork MCP로 내 서버 권한과 환경을 조회해줘. 메인 환경이 READY인지, Discord가 설정됐는지 확인해줘.

`submit_job`, `cancel_job`, `register_ssh_environment`를 포함한 10개 도구가 보여야 한다.
이름만 보이는 것으로 끝내지 말고 사용자 인증·환경 등록·알림 설정을 확인한다.
자동 스킬 선택은 모든 셸 명령을 강제로 가로채는 기능은 아니다. [MCP 안내](mcp-setup.md)를 참고한다.

읽기 전용 연결 검사는 다음과 같다. 설치한 Python으로 실제 stdio MCP를 호출하며 계산은 제출하지 않는다.

```sh
"$COWORK_BIN/python" "$COWORK_SOURCE/scripts/check_mcp.py" \
  --hub-url "$COWORK_HUB_URL" \
  --token-file "$COWORK_ROOT/state/user.token" \
  --runner-config "$COWORK_ROOT/state/runner.json"
```

각 조회의 `ok: true`는 조회 성공을 뜻한다. 작업을 실행하기 전에는 **환경 READY·서버 권한·Discord 설정**도
웹이나 에이전트 조회 결과로 확인한다. Google 로그인·도구 목록 확인만으로 이 검증을 대신하지 않는다.

## 5. 다른 서버의 개인 컨테이너 추가 (선택)

메인 환경에서만 작업하면 건너뛴다. 메인 컨테이너에서 대상의 본인 계정으로 SSH 키 접속이 되어야 한다.
웹에서 연결을 요청하기 전에 **작업을 보낼 메인 컨테이너의 터미널**에서 공개키를 등록한다.
아래 `{port}`, `{user}`, `{ip}`를 대상 컨테이너의 SSH 포트·본인 계정·접속 주소로 바꾼다.

```sh
ssh-copy-id -p {port} {user}@{ip}
```

비밀번호를 요청하면 대상 계정의 비밀번호를 터미널에 입력한다. 기존에 비밀번호 없이 SSH 키 접속이
되면 다시 할 필요는 없다. 처음 연결할 때 대상 호스트를 확인한다.
키 등록 후 비밀번호 입력 없이 접속되는지 확인한다. 다음은 접속 확인 예시이며 계정·주소·포트를 본인 값으로 바꾼다.

```sh
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -p 11010 alice@203.255.11.229 id
```

SSH 접속은 허브의 서버 사용 허가와 별개다. 관리자에게 허용받은 서버에만 등록할 수 있다.
에이전트에는 다음처럼 요청한다.

> 229 서버의 alice@203.255.11.229, SSH 포트 11010, 작업 경로 /10Gdata/alice/work를 cowork 환경으로 등록해줘.

MCP가 본인 SSH로 검사·등록하고 메인 실행기에 경로를 저장한다. 새 환경은 등록 검사를 통과하면
바로 `READY`가 되어 실행할 수 있다. 대상에는 별도 에이전트·MCP 설치가 필요 없다.
단, 공유된 실행기와 Python을 사용할 수 있고 대상에서도 허브에 접속할 수 있어야 한다.

에이전트 없이도 웹의 **작업할 컨테이너 → 다른 서버의 내 컨테이너 연결**에서 등록할 수 있다.
메인 연결 프로그램과 허용 서버를 선택하고 `ssh -p 11010 alice@203.255.11.229`처럼 평소 접속 명령을
붙여 넣는다. **입력 내용 확인**에서 주소·포트·계정을 확인한 뒤 **컨테이너 연결 요청**을 누른다.
입력 내용 확인은 명령을 해석해 보여주는 단계이며, 실제 SSH 접속 검사는 연결 요청 후에 진행한다.
웹 입력란에는 `ssh-copy-id`가 아닌 접속 명령 `ssh`를 입력한다.
**컨테이너 연결 요청**은 메인 연결 프로그램이 SSH로 대상의 UID/GID·공유 경로 등 실행 조건을 확인하고,
이미 있는 컨테이너를 Cowork의 작업 대상으로 등록하는 절차다. 새 컨테이너 생성이나 계산 실행이 아니다.
기본 포트 22는 생략할 수 있다. 추가 SSH 옵션이나 원격 실행 명령은 입력하지 않는다.
설치 기준 경로는 메인 등록에서 재사용한다. 프로젝트 경로는 매 작업에 지정하므로 여기서 입력하지 않는다.
상주 연결 프로그램이 처리하며 등록 요청 → SSH·실행 조건 확인 → 자동 등록·사용 가능 순으로 확인한다.
컨테이너별 추가 승인은 없다. 기존 키 접속이 없다면 먼저 본인 SSH 인증을 준비해야 한다.

## 6. 첫 작업 실행

먼저 메인 환경의 `READY`와 Discord 목적지 설정을 확인한다. 첫 실행은 작은 명령으로 점검한다.

```sh
"$COWORK_BIN/cowork-run" --config "$COWORK_ROOT/state/runner.json" \
  --cpus 1 --mem 64MiB --name first-test --detach -- /bin/echo cowork-ok
```

작업 ID와 로그 경로가 나오면 접수된 것이다. 자원이 부족하면 실행기가 기다렸다가 실행한다.
Discord에서 실제 시작·종료 알림을 받고 출력된 로그 경로에서 `cowork-ok`를 확인한다.
웹 **내 작업**에서 종료된 작업을 보려면 **완료된 작업 포함**을 체크한다.
이것은 사용자가 실행할 점검 절차이며, 이 안내를 작성하면서 새 계산 작업을 제출하지는 않았다.

에이전트로 첫 작업을 실행하려면 같은 조건을 자연어로 전달한다.

> 메인 환경에서 /bin/echo cowork-ok를 CPU 1개, 메모리 64MiB로 실행해줘. 부족하면 대기열에 넣고, 접수 후에는 감시하지 말고 마무리해줘.

MCP와 수동 명령 중 **한 방식만** 선택한다. 둘 다 실행하면 별도 작업 두 건이 된다.
본 작업도 다음처럼 제출한다. 아래 분석 파일·Python은 사용자가 실제 준비한 환경의 것으로 바꾼다.

```sh
"$COWORK_BIN/cowork-run" --config "$COWORK_ROOT/state/runner.json" \
  --cpus 8 --mem 32GiB --detach -- python /10Gdata/alice/work/analysis.py --threads 8
```

`--cpus 8`은 허브 예약량, `--threads 8`은 해당 분석 프로그램의 실행 옵션이다.
GPU가 필요한 작업은 GPU가 준비된 환경에서 `--gpus 1`처럼 요청한다. GPU 한 장은 작업 하나가 예약한다.
수동 CLI는 현재 컨테이너에서 실행하며 자원 부족 시 대기한다. 자동 서버 선택·축소 질문은 하지 않는다.
다른 서버에서 수동 실행하려면 그 컨테이너에 SSH로 접속해 **그 환경의 실행기 설정**으로 호출한다.
메인 설정의 호스트 정보만 바꿔 원격 실행으로 사용하지 않는다. 메인에서의 SSH 제출은 MCP가 지원한다.

MCP는 자원 검토 후 대기·준비된 축소안·다른 준비된 서버 중 선택을 도울 수 있다.
MCP가 실행하는 환경은 대화형 셸의 conda·환경변수와 다를 수 있다. 실제 분석에서는 절대 실행 파일
경로나 환경을 준비하는 진입 스크립트를 지정한다. threads는 해당 프로그램이 지원하는 옵션을 사용한다.
접수 후에는 에이전트를 종료해도 실행기가 대기·실행·종료 보고를 하고 허브가 Discord 알림을 보낸다.
메인/대상 컨테이너의 중지는 에이전트 종료와 다르며, 그 안의 실행 중인 프로그램도 중단될 수 있다.

## 7. 상태 확인·취소·재시작

상태는 웹 **내 작업**에서 확인한다. 에이전트에는 작업 ID로 상태 조회나 취소를 요청한다. 수동 이용자는 사용자 API
`GET /v1/jobs/{id}`, `POST /v1/jobs/{id}/cancel`을 사용한다. 별도 상태·취소 CLI는 아직 없다.
Ctrl-C나 터미널 종료는 작업 취소가 아니다. 취소 요청 후 실제 `CANCELLED`가 되어야 종료된 것이다.
웹에는 현재 작업 취소 버튼이 없다.
접수 응답이 불확실하면 기존 작업 ID·기록을 먼저 확인한다. 같은 CLI를 다시 실행하면 새 작업이 될 수 있다.

자동 시작 등록을 마친 설치는 컨테이너의 Supervisor가 연결 프로그램을 자동 실행한다.
미등록 환경에서만 본인의 절대 경로로 `cowork-connector start --config ...`를 수동 실행한다.
별도 프로세스 관리자를 쓰는 환경은 `cowork-connector startup --config ...`로 스크립트를 만들고
기존 시작 절차에 연결한다. 스크립트 생성만으로 자동 시작이 설정되지는 않는다.
재시작 때마다 설치·새 토큰 발급·재등록할 필요는 없다.
연결 프로그램 시작은 SSH 등록 요청 처리를 다시 켜는 것이며, 중단된 계산을 자동으로 재개하지 않는다.
컨테이너를 새로 만들거나 교체했다면 기존 설정을 그대로 쓰지 말고 별도 환경 등록을 확인한다.

| 막힌 지점 | 확인할 내용 |
| --- | --- |
| 허브 연결 실패 | 내부망 접근과 관리자가 안내한 허브 주소 |
| 인증 실패 | 본인 토큰, 파일 소유자·권한, 토큰 유효성 |
| `USER_IDENTITY_REQUIRED` / `IDENTITY_MISMATCH` | 관리자 기준 UID/GID와 현재 계정 |
| `FORBIDDEN_NODE` | 본인에게 허용된 서버 ID |
| 환경이 `READY`가 아님 | 허용 서버·UID/GID·자원 설정과 허브 버전을 확인. 계정 승인과 컨테이너 등록은 구분 |
| `NOTIFICATION_NOT_CONFIGURED` | 본인 Discord 채널의 허브 연결 |
| SSH 등록 실패 | 키 접속·호스트 확인·공유 경로·대상의 Python과 허브 접근 |
| `UNKNOWN` 또는 실행기 장애 | 실제 프로세스와 기존 기록을 관리자와 확인. 바로 재제출하지 않음 |

오류를 문의할 때는 단계 번호·오류 코드·환경/작업 ID를 전달한다. 토큰 내용과 SSH 비밀키는 보내지 않는다.
웹 운영 설정은 [Firebase Hosting 안내](firebase-hosting.md), 관리자 권한 처리는 [서버 관리 안내](server-platform.md)를 따른다.
