# 허가를 기다리는 로컬 실행 스크립트

허브는 자원 예약·대기열·실행 허가를 관리한다. `cowork-run`의 실행기가 현재 컨테이너에서 명령을
실행하고 실제 시작·종료를 보고한다. Docker 관리 소켓, 호스트 Worker, 허브의 SSH 접속은 필요 없다.
다른 컨테이너에서는 메인 MCP가 사용자 SSH로 같은 실행기를 시작할 수 있다.
대상에 별도 에이전트나 MCP 설치는 필요 없다. [SSH 실행 안내](ssh-runner.md)를 참고한다.

## 구현과 확인 범위

- 사용자 토큰으로 본인 환경·작업만 신청·조회·보고한다. 노드 전체 Worker 토큰은 사용하지 않는다.
- 허브는 CPU·메모리·물리 GPU 예약을 먼저 확정하고, 실행기는 작업별 허가를 한 번만 받는다.
- 실행기는 약 1초 간격으로 상태를 확인한다. 정상 종료 보고가 접수되면 허브는 같은 트랜잭션에서
  다음 작업을 배정한다. 실제 명령 시작에는 조회·통신 시간이 더해지며 0초 전환을 보장하지 않는다.
- 별도 프로세스로 대기·실행하므로 에이전트나 조회용 터미널이 종료되어도 유지된다.
- 명령 인자 배열·작업 경로·종료코드를 보존한다. 제출 프로세스의 환경변수를 실행기가 상속하며
  이를 허브에 복사하지 않는다. alias나 셸 함수는 실행 파일이 아니므로 스크립트 안에서 준비한다.
- Linux subreaper로 남은 자식 프로세스의 종료까지 기다린다. 취소도 해당 작업의 실행기가 수행한다.
- 시작·종료 이벤트를 개인 JSON 기록에 저장하고 재시도한다. 중복 보고는 예약을 다시 반환하지 않는다.
- 실행기 연결이 끊기면 그 작업만 `UNKNOWN`으로 유지한다. 다른 실행기의 상태 보고가 이를 숨기지 않는다.
- 실행 중 실행기가 비정상 종료되면 자동 재실행하지 않는다. 실제 프로세스와 기록을 대조해야 한다.
- 로그는 출력된 `log_path`에 보관한다. 기본 CLI는 완료까지 상태를 조회하고 원래 종료코드를 반환한다.
  Ctrl-C는 조회만 중단한다. 작업 취소는 기존 사용자 취소 API로 요청한다.
- 자원 사용량을 강제 제한하지 않는다. `--cpus`는 예약량이며 프로그램의 threads 인자는 따로 지정한다.

실제 Linux 프로세스와 임시 HTTP 허브로 대기 전환, 실패·취소, 자식 프로세스 대기,
보고 응답 유실, 중복 허가, 잘못된 소유자 차단, 재시작 시 중복 실행 방지를 시험했다.
2026-09-18 운영 허브 배포 후 226에서 작업 두 건의 대기·자동 전환·정상 종료와 실제 Discord 전송 4건도
확인했다. [226 운영 검증 기록](verification-226.md)을 참고한다. `226`에는 GPU가 없다.
2026-09-19에는 같은 실행기를 SSH로 시작해 229의 RTX 3090 장치 선택·CUDA 메모리 접근과
GPU 대기·자동 전환도 확인했다. [229 운영 검증 기록](verification-229.md)을 참고한다.
MCP의 `submit_job`도 같은 실행기를 사용한다. `cancel_job`으로 취소를 요청할 수 있다.
[MCP 연결 안내](mcp-setup.md)에 자원 부족 시 선택지와 중복 제출 방지 규칙을 정리했다.

## 현재 컨테이너 설정

설정 파일은 `.local/runner-226.json`이며 UID `1101`, GID `1100`, 사용자 지정 물리 서버 `226`이다.
개인 토큰은 기존 파일 경로로 참조하며 설정에 토큰 값을 복사하지 않는다.
호스트 이름은 잘못된 컨테이너 설정 사용을 발견하는 보조 수단이며 물리 서버의 증명이 아니다.
물리 서버 대응은 관리자가 확인하고, 사용자별 허용 서버와 UID/GID 정책도 적용한다.
컨테이너를 복제하거나 다른 서버에서 쓰려면 별도 설정·인스턴스로 등록한다.

새 컨테이너에서는 다음처럼 준비한다. 이 명령은 조회와 설정 파일 작성만 수행한다.

```sh
.venv/bin/python scripts/prepare_local_runner.py \
  --node 226 --hub-url http://192.168.10.41:8080 \
  --token-file .local/credentials/user-ezy.token \
  --output .local/runner-226.json
```

이 준비 도구는 CPU 환경만 등록한다. GPU 환경은 보이는 물리 GPU UUID를 확인한 별도 등록이 필요하다.

## 기존 허브 업데이트와 등록

**기존 허브를 실행한 Compose 호스트 터미널에서** 다음을 실행한다.
이때 Docker는 허브 애플리케이션 업데이트에만 사용하며 계산 컨테이너를 관리하지 않는다.

```sh
cd /10Gdata/ezy/01_Programs/cowork-mcp
python3 scripts/enable_local_runner.py \
  --config .local/runner-226.json --user ezy --upgrade \
  --discord-metadata .local/discord-metadata.json
```

- 실행 중 SQLite를 `/data/hub-before-local-runner-<시각>.sqlite3`에 백업한다.
- `hub` 서비스만 빌드·재생성한다. DB 스키마 3은 기존 행·토큰을 보존하고 로컬 실행용 테이블을 추가한다.
- 허브 안의 관리자 인증으로 ezy의 UID/GID와 환경→서버 대응을 등록·승인한다.
- 설정 파일에 환경 ID를 반영한다. 같은 설정으로 다시 실행해도 기존 환경 ID를 유지한다.
- 기존 Discord `.env`를 Compose `env_file`로 참조한다. Webhook 값을 새 파일에 복사하지 않는다.
  확인한 서버·채널 ID와 ezy 소유권을 대조하고 알림 목적지를 연결한다. 적용 중에는 알림을 보내지 않는다.
- 관리자 토큰은 허브 밖으로 꺼내지 않는다. 기존 사용자 권한·서버 예산을 추가하거나 변경하지 않는다.

업데이트가 이미 끝났으면 `--upgrade`를 생략한다. Discord 설정은 `.local/compose.local-runner.yaml`에
기존 설정 파일 경로로 보관하므로 이후에도 이 적용 도우미를 사용하거나
`docker compose -f compose.yaml -f .local/compose.local-runner.yaml ...`로 관리한다.
기본 Compose 파일만 사용해 재생성하면 추가 알림 설정이 빠질 수 있다. 데이터 복원은 허브를 중지한 뒤 백업을 기준으로
수행해야 하며, 운영 중 DB 파일만 덮어쓰지 않는다.

Discord 목적지가 미등록이면 현재 제출 정책에 따라 실행을 막는다. 가짜 알림 목적지를 운영 허브에
등록하거나 예약 없이 로컬 실행으로 우회하지 않는다. 사용자 채널 연결 후 시험 작업을 제출한다.

## 명령 실행

허브 업데이트·환경 승인·Discord 목적지 연결을 마친 후 현재 컨테이너에서 실행한다.

```sh
scripts/cowork-run --config .local/runner-226.json \
  --cpus 1 --mem 64MiB -- /bin/echo hello

# 에이전트/SSH가 기다리지 않고 작업 ID·로그 경로를 받고 돌아오기
scripts/cowork-run --config .local/runner-226.json \
  --cpus 8 --mem 32GiB --detach -- python analysis.py --threads 8
```

`--` 뒤는 하나의 명령과 인자다. 파이프·리다이렉션·여러 단계는 `bash pipeline.sh`처럼 명시한다.
표준 입력을 요구하는 대화형 명령은 지원하지 않는다. 로그 내용은 허브나 Discord로 전송하지 않는다.
같은 작업을 다시 제출하면 새 작업이므로, 접수 응답이 불확실하면 출력된 기록을 확인하고 재제출하지 않는다.

## API

| 호출 | 인증과 범위 |
| --- | --- |
| `GET /v1/capabilities` | 공개 기능 확인, `local_runner: 1` |
| `POST /v1/local/environments` | 사용자 본인의 허용 서버에 등록 요청 |
| `POST /v1/admin/local/environments/{id}/approve` | 관리자의 환경→서버 대응 확인 |
| `POST /v1/local/jobs` | 본인 환경 하나와 실행기 ID로 명령·자원 신청 |
| `POST /v1/local/jobs/{id}/poll` | 본인 작업 상태 조회·해당 실행기 연결 갱신 |
| `POST /v1/local/jobs/{id}/claim` | 예약된 작업에 대한 한 번의 실행 허가 |
| `POST /v1/local/jobs/{id}/events` | 같은 사용자·실행기·허가 시도의 실제 결과 보고 |

기존 서버 Worker API는 호환용으로 유지하지만 로컬 환경을 변경하거나 로컬 작업을 처리할 수 없다.
현재 환경의 `READY`는 승인 상태다. 서버의 `online`은 기존 Worker 또는 본인 실행기의 최근 활동을
나타내므로 로컬 작업이 없는 동안 `false`여도 설정된 컨테이너에서 새 실행 스크립트를 시작할 수 있다.
