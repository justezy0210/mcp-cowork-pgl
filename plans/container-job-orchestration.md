- 사용자별 허용 서버 목록을 관리한다. 예: 사용자 1은 A·B, 사용자 2는 B·C. 공유 서버 B의 예약량은 모든 사용자를 합산한다.
- 사용 가능한 서버에 개인 실행환경을 준비할 수 있다. 실제 준비된 컨테이너만 배정 후보로 등록한다.
- 첫 버전은 사용자가 미리 준비해 등록한 개인 컨테이너만 사용한다. 컨테이너 자동 생성·환경 복제는 포함하지 않는다.
- 첫 버전은 신청한 CPU·메모리 양과 GPU 장치를 기준으로 예약한다. GPU 한 장은 동시에 작업 하나에만 예약한다. 작업별 실제 사용량 강제 제한은 요구하지 않는다.
- 사용자는 새 개인 컨테이너를 준비한 뒤 SSH 접속 경로를 입력해 직접 등록할 수 있다. 등록은 기존 서버 사용 권한을 확장하지 않는다.
- 원래 요청을 당장 충족할 수 없고 실행 가능한 축소안이 있으면, 에이전트가 사용자에게 원래 조건으로 대기할지 축소해서 실행할지 묻는다. 승인 없이 자원을 축소하지 않는다.
- 모든 서버에 관리자 권한으로 필요한 서비스를 설치할 수 있다.
- 첫 버전의 실행 단위는 명령·스크립트 한 개다. 여러 단계가 들어 있는 스크립트도 작업 한 건으로 관리한다.
- 대기열은 접수 순서로 검토하되 현재 허용 서버·실행환경·자원 조건을 만족하는 작업부터 배정한다.
- 실제 작업 시작과 종료를 사용자에게 Discord로 알린다. 동일한 Discord 서버 안에 사용자별 채널을 마련하고 해당 사용자의 작업 알림을 그 채널로 보낸다.

## 초기 범위와 가정

초기 범위는 사용자가 선택한 명령·스크립트 단위의 배치 작업이다. 기존 SSH 대화형 개발 환경은 유지하되 Jupyter 등의 세션 자체를 이동하거나 예약하는 기능은 포함하지 않는다. 실제 작업 예시와 실행 옵션은 구현 시작 시 확인한다.

작업 한 건은 전체 실행 동안 신청한 CPU·메모리를 예약하고, 해당 명령과 필요한 하위 작업의 종료·정리를 확인한 뒤 반환한다. 여러 단계를 순서대로 실행하는 스크립트는 각 자원의 최대 필요량을 신청한다. 내부에서 여러 계산을 동시에 실행하면 그때의 합산 필요량을 고려한다. 단계별 예약 반환·재배정은 첫 버전 범위에 포함하지 않는다.

컨테이너 생성·환경 복제는 사용자 또는 관리자의 운영 준비 절차로 둔다. 시스템은 준비해 등록한 기존 개인 컨테이너에서만 실행하며, 작업 제출 중에 컨테이너를 자동 생성하거나 환경을 복제하지 않는다. 허용 서버라도 본인의 등록된 실행환경이 없으면 배정 후보에서 제외한다. 실행 중인 작업의 서버 간 이동은 포함하지 않는다. 자동 재실행, 고가용성, 정교한 사용자별 우선순위는 현재 제안하는 첫 버전 범위 밖이다. 웹 플랫폼은 구축 범위에 포함하며, 현황 조회와 운영 관리부터 단계적으로 구현한다. GPU 예약은 첫 버전에 포함하며 한 장당 작업 하나가 예약한다. 한 작업이 여러 장을 요청할 수 있지만 각 장은 다른 작업과 중복 예약하지 않는다. GPU 메모리 분할 공유와 MIG·MPS 공유 스케줄링은 포함하지 않는다. 실제 GPU 제조사·드라이버는 현장 확인하며, 아래 실행환경 설정 예시는 NVIDIA CUDA 기준이다.

## 수동 사용자용 명령 접두 도구

`cowork-run`은 일반 사용자가 개인 컨테이너에서 호출하는 제출 CLI로 만든다. 아래는 **구현 예정 사용법**이며 현재 실행 가능한 명령이 아니다.

```bash
# 기존 실행
python analysis.py --threads 8

# 같은 계산을 허브에 제출: 메모리 32 GiB, GPU 사용 없음
cowork-run --cpus 8 --mem 32GiB --gpus 0 -- python analysis.py --threads 8

# GPU 작업 또는 여러 단계를 포함한 스크립트
cowork-run --cpus 8 --mem 32GiB --gpus 1 -- bash train.sh
```

### 공통 실행 경로

- 사용자가 한 번 설정한 허브 주소·본인 인증 토큰·기본 실행환경 프로필을 사용한다. 프로필에는 후보로 사용할 본인의 검증된 환경 목록을 저장한다. 한 환경만 지정하면 그 컨테이너에서 대기하고, 여러 환경을 지정하면 기존 정책대로 가능한 서버에 배정한다.
- 자원량은 CLI 옵션 또는 사용자가 미리 지정한 프로필에서 가져온다. 명령을 보고 CPU·메모리 요구량을 임의 추측하지 않는다. `--cpus 8`은 예약 요청이며 실제 프로그램의 `--threads 8`을 자동 삽입하거나 바꾸지 않는다.
- CLI는 검토·제출·조회·취소 API를 사용한다. 셸 프로세스가 직접 자원을 예약하거나 계산을 실행한 뒤 `trap`으로 반환하는 별도 경로를 만들지 않는다. 접수 이후의 대기·실행·종료 관측은 기존 허브·Worker가 수행한다.
- 허브 접속 실패, 인증 실패, 알림 미설정, 등록 환경 미검증은 오류로 안내한다. 실패했다고 원래 명령을 예약 없이 로컬에서 실행하지 않는다.
- 토큰은 권한을 제한한 사용자 설정 파일에서 읽고 명령 인자·출력·로그에 넣지 않는다. 수동 사용자도 에이전트 없이 초기 설정, 환경 등록·목록, 채널 연결, 작업 조회·취소를 할 수 있도록 `cowork` 관리 CLI를 함께 제공한다. 사용자에게 Worker 토큰이나 Docker 관리 소켓은 제공하지 않는다.

### 터미널 동작과 선택

- 초기 기본 동작은 작업 ID와 대기·실행 상태를 표시하며 완료까지 조회하는 방식으로 둔다. 정상적으로 종료 결과를 받으면 원래 명령의 종료코드를 셸에 반환한다. 로그는 Worker의 작업 로그로 보존하며 본인 로그를 제한된 분량으로 조회할 수 있게 연결한다.
- `--detach`는 접수 확인과 작업 ID를 받은 뒤 즉시 반환한다. 이때 종료코드 0은 접수 성공이며 계산 성공을 뜻하지 않는다. 터미널 종료나 CLI 연결 단절 후에도 이미 접수된 작업은 진행되고 Discord 알림을 받는다.
- 화면 조회 중 Ctrl-C는 조회만 중단하며, 작업이 유지된다는 안내와 작업 ID를 출력한다. 실제 취소는 `cowork cancel JOB_ID`로 명시적으로 요청한다. 조회 실패·연결 단절을 계산 실패로 표시하지 않는다.
- 자원이 부족하면 기본적으로 원래 신청량으로 대기한다. 즉시 시작만 원하는 옵션은 `start_if_available`에 대응시키며 실패 시 몰래 대기 등록하지 않는다.
- 축소안은 사용자가 실제 명령·자원량을 함께 준비한 경우만 검토한다. 대화형 터미널에서 원래 조건으로 대기할지 준비된 대안을 선택할지 묻고, 입력을 받을 수 없는 실행에서는 명시한 실행안·제출 정책만 적용한다. 일반 프로그램의 threads·메모리·GPU 옵션을 임의로 고치지 않는다.
- 최초 전송 전에 재시도 키와 제출 내용을 사용자 측에 보존한다. 접수 응답이 유실되면 같은 키·같은 내용으로 확인하며 새 작업을 중복 생성하지 않는다. 키 보존 기록에는 인증 토큰을 포함하지 않는다.

### 명령과 실행환경 보존

- `--` 뒤의 인자 배열을 그대로 전달한다. 공백·따옴표를 보존하고 문자열 전체를 `eval`하지 않는다. 파이프·리다이렉션·여러 명령을 작업 하나로 묶으려면 `bash pipeline.sh`처럼 스크립트로 제출한다. 접두어 바깥의 `|`나 `>`까지 자동으로 원격 실행된다고 설명하지 않는다.
- 제출 시 현재 작업 경로를 작업별 실행안에 기록한다. 이를 위해 현재 환경 등록에만 있는 `workdir`과 별도로 **작업별 `workdir`을 허브 요청·저장·배정에 추가**한다. 기존 API 요청이 이를 생략하면 등록 환경의 작업 경로를 사용하는 호환성을 유지한다.
- 실행 후보 컨테이너에서 같은 작업 경로·입력·프로그램에 접근할 수 있는지 확인한다. NFS를 사용해도 마운트 경로와 프로그램 환경이 같다고 가정하지 않는다. Worker가 실행 직전에 다시 확인하고 실패하면 원인을 보고한다. 허브가 사용자 파일이나 실행환경을 자동 복사하지 않는다.
- 현재 SSH 셸에서 활성화한 conda·가상환경, alias, 셸 함수, 모든 환경변수를 자동 전달하지 않는다. 등록된 실행환경, 명시한 실행 파일 경로 또는 환경을 준비하는 진입 스크립트로 실행 조건을 고정한다.
- 수동 명령도 기존 명령·스크립트 단위 배치 작업 범위를 따른다. 대화형 stdin·TTY 프로그램, 임의 터미널 세션 이동은 첫 버전 범위에 추가하지 않는다.

## 구조

```text
웹 브라우저 → 현황·관리 화면 ───────┐
Claude·Codex → MCP 어댑터 ──────────┤
수동 터미널 → cowork-run / cowork ─┤
                                  ↓
                      공통 허브 API + 영속 작업 DB
                                  ↓
                            서버별 Worker
                                  ↓
                 사용자의 등록된 Docker 컨테이너에서 작업 실행
```

| 구성 | 책임 |
| --- | --- |
| 공통 스킬 | 실행 명령·환경·자원 요구량 준비, 축소안 설명과 사용자 선택, 작업 ID·로그 경로 전달 |
| 웹 플랫폼 | 역할별 현황 조회, SSH 접속 환경 등록과 서버·사용자 권한·알림 설정 요청을 공통 허브 API에 전달 |
| MCP 어댑터 | 인증된 사용자의 검토·제출·조회·취소 요청을 중앙 서비스에 전달 |
| 수동 제출·관리 CLI | 명령 인자·작업 경로·신청량을 같은 API에 제출, 선택적 완료 조회, 에이전트 없는 설정·환경 등록·조회·취소 |
| 중앙 서비스 | 접근 정책, 후보 서버 선택, 원자적 자원 예약, 대기열, 작업 상태, 이벤트 중복 처리 방지, 사용자별 알림 대기 기록 |
| 알림 전송 루프 | 중앙에 기록된 시작·종료 알림을 사용자별 Discord 채널로 전송하고 실패 시 재시도 |
| 서버 Worker | 컨테이너 확인, 실행·종료 감지, 로그·결과 보관, 완료 보고 재전송, 재연결 시 상태 대조 |
| 컨테이너 내 실행 래퍼 | 작업별 실행 식별자와 프로세스 그룹 관리, 명령과 하위 작업 대기, 종료 결과 기록 |

Worker와 중앙 서비스는 사용자 SSH 세션과 별개의 상주 서비스로 운영한다. 컨테이너 작업 실행에는 Docker exec 기능을 사용하되, 작업을 에이전트의 SSH 프로세스에 매달지 않는다. 컨테이너 재시작으로 중단된 작업은 정상 완료나 자동 재실행으로 처리하지 않는다.

소규모 첫 구현은 Python 서비스와 중앙 호스트 로컬 디스크의 SQLite를 기본 후보로 삼는다. 실행 중인 DB 파일을 NFS에 두거나 각 Worker가 공유 파일로 직접 수정하지 않는다. NFS는 입력·결과·로그 공유에 사용한다. 라이브러리와 배포 방식은 설치 환경을 확인한 뒤 고정한다.

### 신호와 정보가 모이는 상주 개체

중앙 서비스의 배포 단위를 가칭 `cowork-hub`로 둔다. 연구실 내부망에서 접근할 수 있는 주소를 가진 상주 애플리케이션이며, 요청 접수 API, 예약·배정 루프, DB 접근을 맡는다. MCP는 이 서비스에 접근하는 에이전트용 인터페이스이고, Worker의 상태·완료 보고는 같은 서비스의 Worker용 API로 직접 전달한다. 이 둘은 논리적 인터페이스 구분이며 별도 서버 두 대를 요구하지 않는다.

항상 켜진 호스트 한 대에 전용 Docker 컨테이너로 실행하는 구성을 우선 제안한다. 기존 스토리지 서버도 후보이지만 여유 자원과 운영 조건을 확인한 뒤 위치를 정한다. 호스트 로컬 디스크의 전용 디렉터리를 컨테이너에 연결해 DB를 보존하고, 중앙 서비스 컨테이너에는 Docker 재시작 정책을 설정한다. 수동 중지 후에는 유지되는 `unless-stopped`를 기본 후보로 둔다. 이는 중앙 서비스의 복구 정책이며 연구 계산 작업의 자동 재실행 정책이 아니다.

| 정보를 보내는 주체 | 중앙 서비스가 받는 정보 | 저장·처리 결과 |
| --- | --- | --- |
| 관리자 | 사용자별 허용 서버, 서버별 계산 예산과 GPU 장치 목록 | 권한과 자원 예산 등록 |
| 사용자 | 본인의 새 컨테이너 이름, SSH 접속 경로, 작업 경로 | 접속·소유권·실제 서버 확인 후 개인 실행환경 등록 |
| 에이전트의 MCP 호출 | 원래·대안 실행안 검토, 사용자가 선택한 실행안의 제출, 조회·취소 | 검토 결과 반환 또는 영속 작업 접수 |
| 수동 사용자의 CLI 호출 | 명령 인자·작업 경로·실행환경·신청량, 검토·제출·조회·취소 | MCP와 같은 권한·예약·대기열로 처리 |
| 로그인한 웹 사용자·관리자 | 역할에 따른 현황 조회, SSH 접속 환경 등록·사용자 권한·예약 예산·배정 가능 상태·알림 설정 변경 | API 권한 검사 후 설정·변경 이력 저장 |
| 서버 Worker | 서버 연결 상태, 등록 컨테이너 준비 상태, 작업 시작 확인 | 새 배정 가능 여부와 실행 상태 갱신 |
| 서버 Worker의 완료 보고 | 작업 ID, 실행 식별자, 종료코드, 결과·로그 위치 | 종료 상태 확정, 예약 반환, 다음 배정 시작 |

서버·사용자 신원은 메시지에 적힌 문자열만으로 결정하지 않고 인증 정보와 등록 정책으로 검증한다. 작업 완료의 근거는 Worker와 실행 래퍼가 관찰한 실제 실행 결과이며, 에이전트의 자연어 완료 선언으로 예약을 반환하지 않는다.

예를 들어 작업 101이 종료되면 Worker가 결과를 로컬에 저장하고 중앙 API에 완료를 보고한다. 중앙은 해당 실행과 일치하는 보고인지 검증한 뒤 완료 상태와 예약 반환을 DB에 반영하고 접수 확인을 보낸다. 배정 루프는 이 변경을 계기로 대기열을 평가하고, 다음 작업의 예약과 배정 의도를 영속 저장한 뒤 해당 Worker에 전달한다. 중앙이 이 과정에서 재시작되면 미처리 배정 의도를 다시 조회하고, Worker의 실행 식별자 중복 방지와 함께 복구한다.

API 접수 확인을 받기 전에는 Worker가 보고를 보관하고 재전송한다. 이벤트는 여러 번 도착할 수 있지만 같은 작업의 예약은 한 번만 반환한다. 중앙 서비스가 중단된 동안에도 Worker는 실행 결과를 보존하며, 새로운 배정은 중앙 복구 후 재개한다. 별도 메시지 브로커는 초기 필수 구성으로 추가하지 않는다. Discord 알림은 같은 DB에 영속 저장한 전송 대기 기록을 별도 루프가 처리하며, 작업 배정 루프가 Discord 응답을 기다리지 않는다.

## 웹 현황·관리 플랫폼

허브를 공통 백엔드로 두고 웹은 그 API를 사용하는 관리 화면으로 구현한다. 웹 전용 예약 DB나
별도 스케줄러를 만들지 않는다. 현재 등록 스크립트는 초기 준비 수단이며, 일상적인 조회·관리 기능은
인증된 API로 옮겨 웹에서 사용할 수 있게 한다. 웹 서버가 SQLite를 직접 수정하는 경로는 만들지 않는다.

웹 관리의 범위는 SSH 접속 환경 추가와 사용자별 서버 이용 제한 등 설정 관리다.
작업·대기열은 현황 조회 대상으로 두며, 작업 제출·명령 실행·취소는 MCP·수동 CLI에서 수행한다.

### 첫 웹 버전의 화면과 권한

| 화면 | 일반 사용자 | 관리자 |
| --- | --- | --- |
| 서버 현황 | 허용 서버의 예산·예약량·추가 예약 가능량, GPU 예약 여부, Worker 연결 상태 | 전체 서버 현황, 서버 등록·예약 예산 변경·새 배정 중지와 재개 |
| 작업·대기열 | 본인 작업의 상태·대기 이유·예약·로그·알림 결과 조회, 허용 서버의 공유 대기열 요약 | 전체 작업의 운영 현황 조회 |
| 사용자·권한 | 본인 설정 조회 | 사용자 등록·비활성화, 사용자별 허용 서버 지정, 인증 정보 발급·회수 |
| 개인 MCP 토큰 | 본인 토큰 발급·목록 조회·개별 폐기 | 사용자 토큰 상태 확인·폐기. 기존 토큰 원문 조회는 제공하지 않음 |
| SSH 접속 환경 | SSH 호스트·포트·계정으로 본인 컨테이너 등록 요청, 검증 상태·작업 경로 확인 | 전체 환경과 등록 문제 확인·환경 배정 중지 |
| 알림 | 본인 Discord 채널 연결 상태·전송 실패 확인 | 목적지 연결·비활성화, 실패 알림 확인·재전송 |

일반 사용자의 공유 대기열 요약에는 타인의 원본 명령·로그·파일 경로를 노출하지 않는다.
관리자는 운영에 필요한 전체 작업 요약을 조회하며, 상세 명령·로그 열람 범위는 명시적으로 정하고
API에 적용한다. 화면의 버튼을 숨기는 것만으로 권한을 구현하지 않는다. 작업 제출 폼·취소 버튼·
코드 편집기·웹 터미널·파일 관리자는 웹 구축 범위에 포함하지 않는다.

SSH 경로 추가는 기존 컨테이너를 허브에 등록하는 절차이며, 사용자에게 새 서버 권한을 부여하지 않는다.
웹에서 입력한 접속 정보는 검증 대기 상태로 저장하고 기존 SSH 접속 증명·Worker 검증 절차를 따른다.
웹 브라우저에 SSH 개인 키를 업로드하거나 브라우저가 직접 SSH 접속하는 기능은 요구하지 않는다.
사용자별 허용 서버는 허브의 제출·배정 시점에 적용하며, 기존 서버의 SSH 로그인 권한을 변경하는 기능과는 구분한다.

### 개인 MCP 토큰 관리

사용자는 웹 로그인 후 본인의 MCP·CLI용 사용자 토큰을 발급하고 관리한다. 현재의
`prepare_mcp_token.py`는 기존 토큰을 개인 환경에 전달하는 초기 설치 수단이며, 웹 발급 기능은 아니다.

- 발급 요청의 사용자 신원은 검증된 웹 로그인에서 결정한다. 허브가 난수 토큰을 생성하고 본인의 사용자 권한으로 연결한다. 브라우저가 임의로 만든 문자열을 인증 토큰으로 등록하지 않는다.
- 새 토큰 원문은 발급 직후 한 번만 전달한다. 사용자가 개인 토큰 파일로 저장하도록 안내하고, DB에는 검증용 해시를 저장한다. 목록·변경 이력·로그에는 원문을 남기지 않는다.
- `226-Codex`처럼 사용 위치를 구분하는 이름을 붙일 수 있게 한다. 새 토큰을 발급해도 다른 컨테이너에서 쓰던 토큰을 자동 폐기하지 않으며, 본인의 토큰을 각각 조회·폐기할 수 있게 한다. 이름은 표시용이며 실제 서버 권한은 허브의 사용자 정책을 따른다.
- 사용자 토큰 발급으로 관리자·Worker 권한이나 새 서버 이용 권한을 얻을 수 없다. 다른 사용자의 토큰 조회·발급·폐기는 일반 사용자에게 허용하지 않는다.
- 폐기된 토큰은 이후 인증에서 거절한다. 이미 접수된 작업의 실행·예약은 토큰 폐기만으로 중단하거나 반환하지 않는다.
- 현재 허브는 사용자당 단일 `token_hash`를 저장하므로, 웹 구현 시 사용자별 여러 자격증명과 개별 폐기를 지원하는 저장 구조·API가 필요하다. 기존 사용자·토큰·예약을 보존하는 이전 절차를 포함하고 관리자·Worker 인증은 역할별로 유지한다.

### 표시와 관리 동작의 기준

- 자원 숫자는 **등록 예산 / 예약량 / 추가 예약 가능량**으로 명확하게 표시한다. 실제 CPU 사용률·메모리 사용량을 수집하지 않는 현재 단계에서 예약량을 실제 사용량처럼 표시하지 않는다. 실제 사용률 그래프는 별도 수집 기능을 구현한 경우에 추가한다.
- 서버 등록 완료와 실제 실행 가능 상태를 구분한다. Worker가 연결되지 않았거나 컨테이너가 미검증이면 그 이유와 마지막 확인 시각을 표시한다. 예약량이 0이라는 이유로 실행 가능하다고 표시하지 않는다. `UNKNOWN`의 예약은 유지한 채 보여 준다.
- 서버 예산 변경은 현재 예약과 같은 트랜잭션에서 검사한다. 이미 예약된 CPU·메모리보다 작은 예산이나 예약 중인 GPU 제거는 거절한다. 등록 예산 변경을 이유로 실행 중인 계산을 임의 중단하지 않는다.
- 새 배정 중지는 그 서버의 신규 배정만 막고 기존 작업·Worker 완료 보고는 유지한다. 권한 회수도 기존에 합의한 새 제출·배정 기준을 따르며, 설정 변경만으로 실행 중인 작업의 예약을 반환하지 않는다.
- 누가 언제 어떤 관리 설정을 바꾸었는지와 변경 전후 값을 감사 기록으로 남긴다. 인증 토큰·Webhook 원문·SSH 비밀정보는 이 기록에 넣지 않는다.
- 작은 연구실 규모에서는 페이지가 열려 있을 때 제한된 주기로 현황을 갱신하고 목록을 페이지 단위로 조회한다. 최근 성공 갱신 시각과 연결 오류를 표시해 오래된 화면을 현재 상태로 오해하지 않게 한다. 화면 갱신은 예약·배정을 수행하지 않는다.

### API·로그인·배포 준비

현재 API에는 관리자용 전체 서버·사용자·작업·환경 목록, 예약 예산 변경, 새 배정 중지·재개,
웹 로그인 세션, 개인 토큰 발급·목록·폐기, 감사 기록과 일부 알림 관리 기능이 없다. 현재 화면으로 관리가 가능하다고 표시하지 않고
필요한 API를 먼저 추가한다. Worker의 실제 시작·종료 보고 권한은 웹 사용자에게 주지 않는다.

브라우저는 사용자별 로그인과 관리자·일반 사용자 역할을 사용한다. 초기 관리자 준비 이후 일상적으로
서버 셸에서 관리자 토큰을 복사해 웹에 붙여 넣는 운영은 피한다. 로그인 수단은 구현 전에 정하며,
브라우저 세션에는 만료·로그아웃·보호된 쿠키와 상태 변경 요청 위조 방지를 적용한다.
현재 MCP·CLI·Worker용 Bearer 인증은 역할별로 유지한다. 공용 관리자 토큰이나 Worker 토큰을
웹 코드·브라우저 저장소에 포함하지 않고, 자격증명 발급이 필요한 경우 본인 권한으로 한 번 전달한다.

초기 웹은 연구실 내부에서 허브와 같은 주소·출처로 제공하는 구성을 기본으로 검토한다.
별도 외부 호스팅이나 인터넷 공개를 전제로 하지 않는다. 웹 화면이 종료되거나 프런트엔드가 재시작되어도
허브·Worker의 예약·실행·완료 보고·Discord 알림은 계속되어야 한다.

## 사용자와 실행환경

- 관리자가 `사용자 → 허용 서버`와 서버·자원 목록을 등록한다. 사용자는 자신의 SSH 접속 경로로 개인 실행환경을 직접 등록한다. 검증된 `(사용자, 서버, 실행환경) → 컨테이너 ID, 실행 UID/GID, 작업 경로, 환경 실행 방법, 접근 가능한 GPU` 대응을 저장한다.
- 사용자 신원은 인증 정보에서 결정한다. 모델이 전달한 사용자 이름을 신뢰하지 않는다.
- 제출과 배정 시점에 허용 서버, 컨테이너 소유권, 준비 상태를 검증한다. 금지 서버를 직접 지정하거나 다른 사람의 컨테이너를 지정하면 거절한다.
- 조회·로그·취소도 소유권을 검사한다. 서버 현황은 자원 요약을 제공하고 타인의 상세 명령·로그를 기본 공개하지 않는다.
- Worker는 승인된 중앙 서비스의 요청만 수락하고 등록된 소유자·컨테이너 대응을 확인한다. 개인 작업 컨테이너에 Docker 관리 소켓을 노출할 필요는 없다.
- 허용 서버 변경은 새 배정부터 적용한다. 대기 중인 작업도 배정 전 재검사한다. 실행 중인 작업의 강제 중단은 별도 취소 동작으로 처리한다.

### UID/GID 운영 규칙

사용자별 Linux 식별자는 다음 규칙으로 운영한다. 사용자별 기준값 저장과 UID 중복 검사,
환경 검증·heartbeat·신규 배정 시 일치 검사를 구현·배포했고 ezy의 기준값 `1101:1100`을 확인했다.
스키마 2는 기존 사용자·토큰·환경·작업·예약을 보존하고 기준값 저장 테이블을 추가한다.
기존 사용자의 기준값을 임의 추론하지 않으며, 관리자 설정 전에는 신규 환경 활성화·배정을 막는다.

- 사람마다 서로 다른 UID를 배정하고, 동일인은 사용하는 모든 서버와 컨테이너에서 같은 UID와 기본 GID를 사용한다. 공동 작업 그룹의 GID는 여러 사람이 공유할 수 있으며, GID를 사용자 고유 식별자로 사용하지 않는다.
- 허브 계정 ID와 Linux 계정 이름은 별개다. 로그인 계정 이름이 달라도 위 숫자 규칙과 소유권 검증을 충족하면 등록할 수 있다. UID/GID 일치만으로 같은 사람이라고 인증하지 않는다.
- 관리자가 허브 사용자별 기준 UID·기본 GID와 허용 서버를 등록한다. 다른 사용자가 이미 쓰는 UID는 중복 등록하지 못하게 하고, 본인이 입력한 SSH 경로로 기준값이나 서버 권한을 변경할 수 없게 한다.
- Worker는 실제 컨테이너의 실행 UID·기본 GID를 확인해 보고하고, 허브는 사용자의 기준값과 대조한다. 기준값이 없거나 값이 다르면 환경을 활성화하지 않고 미설정·불일치 이유를 표시한다. UID/GID가 맞더라도 접속 증명·소유권·허용 서버 검사를 통과해야 한다.
- Docker의 UID/GID 재매핑이 있으면 호스트·공유 저장소에서의 대응도 확인한다. 컨테이너 안 숫자가 같다는 사실만으로 NFS 접근 가능 여부를 확정하지 않고, 실제 작업 경로의 접근 권한을 확인한다.
- 기존 사용자 기준값은 관리자가 확인한 값으로 등록한다. 규칙 적용을 위해 시스템이 기존 Linux 계정 번호나 파일 소유권을 자동 변경하지 않는다. 기준값을 변경하면 관련 환경을 재검증하고, 기존 실행 중인 작업의 식별자·예약은 임의 변경하지 않는다.

현재 구현은 기존 검증 환경과 충돌하는 기준값 변경을 `IDENTITY_IN_USE`로 거절한다.
환경 교체·재검증을 통한 기준값 변경 절차는 후속 구현 대상이며, 값 변경만으로 기존 환경을
다른 UID/GID의 실행환경으로 바꾸지 않는다. 허용 서버 권한과 Worker의 기존 검증 절차도 유지한다.

### SSH 접속 경로를 통한 사용자 등록

예시 입력은 `ssh -p 2222 researcher@server-b` 또는 `ssh://researcher@server-b:2222`이다. 사용자가 이를 에이전트에 전달하면 `register_environment`가 등록을 시작한다. SSH 명령 형식의 입력은 허용된 접속 필드로 파싱하며, 입력 문자열 전체를 셸 명령으로 실행하지 않는다. 등록 정보는 SSH 호스트·포트·로그인 계정, 환경 표시 이름, 작업 경로와 실제 실행환경 식별자로 구성한다.

1. 인증된 사용자의 등록 요청을 만들고 `PENDING_VERIFICATION` 상태로 저장한다. 서버·컨테이너에 대한 확인 전에는 배정 후보가 되지 않는다.
2. 사용자의 기존 SSH 인증 수단이 있는 위치에서 접속을 확인한다. SSH 별칭은 그 위치의 설정을 이용해 호스트·포트·계정 등의 구체적인 접속 정보로 해석한다. 호스트 키 검증을 생략하지 않으며, SSH 개인 키나 비밀번호 원문은 MCP 인자·중앙 DB·로그로 복사하지 않는다. 점프 호스트와 특수 SSH 설정의 지원 범위는 실제 접속 예시로 확인한다.
3. 중앙이 사용자와 등록 요청에 묶인 짧은 유효기간의 일회성 검증값을 발급하고, 접속한 컨테이너에서 이를 사용해 등록 확인 절차를 수행한다. 해당 노드의 신뢰된 Worker가 Docker 런타임을 통해 검증값을 가진 실제 컨테이너 ID와 실행 사용자 대응을 확인한다. 컨테이너가 스스로 주장하는 호스트 이름이나 사용자가 입력한 서버 이름만으로 물리 서버를 확정하지 않는다. 공유 NFS 경로에서 검증값이 발견되었다는 사실만으로 컨테이너를 식별하지 않는다. 신뢰된 Worker가 실제 실행 컨텍스트와 UID를 함께 확인해야 한다. 구체적인 검증값 전달·확인 방식은 실제 SSH·Worker 접근 경로를 확인한 뒤 구현한다.
4. 확인된 물리 서버가 사용자의 허용 목록에 있는지 검사하고, 기존 소유자 등록과 충돌하지 않는지 확인한다. Worker가 없는 서버는 관리자가 먼저 서버를 등록해야 한다. SSH 접속 성공 자체가 새 서버 사용 권한을 부여하지 않는다.
5. 컨테이너 내부 UID/GID를 위 운영 규칙의 사용자 기준값과 대조하고, 작업 경로, 환경 실행 방법, 기존 자원 한도, 보이는 GPU 장치를 확인한다. GPU를 사용할 수 없는 컨테이너는 CPU 작업용으로 등록할 수 있지만 GPU 작업 후보로는 사용하지 않는다.
6. 검증된 대응과 환경 프로필을 저장해 `ACTIVE`로 전환한다. 이후 작업은 기존 설계대로 호스트 Worker가 등록된 컨테이너 안에서 실행한다. 등록에 사용한 SSH 세션은 실행·대기를 유지하는 데 필요하지 않다. 등록 후 준비 상태는 Worker와 실제 컨테이너를 기준으로 판단하며 최초 SSH 세션 종료만으로 환경을 비활성화하지 않는다.

컨테이너 접속 권한 확인과 중앙의 사용자별 서버 정책을 함께 적용한다. 이미 다른 사용자의 환경으로 등록된 컨테이너의 소유자를 임의로 바꾸지 않는다. 같은 컨테이너를 다른 SSH 별칭으로 등록해도 새 서버나 별도 자원으로 계산하지 않는다. 컨테이너 이름을 재사용해 새 컨테이너를 만들거나 실제 접속 대상이 바뀌면 새 컨테이너 ID를 검증해야 하며, 새 컨테이너 ID는 새 등록 버전으로 저장하며 기존 작업이 참조하는 등록 버전과 대상은 바꾸지 않는다.

## 신청량에 따른 자원 관리

노드마다 관리자가 계산에 사용할 CPU·메모리 예산을 설정한다. 호스트 운영체제, 상주 개인 환경, 허브를 거치지 않는 기존 직접 실행 작업을 위한 여유는 이 예산에서 제외한다. `cowork-run`으로 제출한 수동 작업은 MCP 작업과 동일하게 이 예산에서 예약한다. CPU 단위는 등록한 논리 CPU 수, 메모리는 내부적으로 MiB로 통일한다. GPU는 물리 서버의 장치 UUID 또는 이에 준하는 안정적인 장치 식별자로 예약한다.

```text
예약 가능량 = 노드의 계산 예산 - 배정 중·실행 중·실행 여부 미확인 작업의 예약 합계
```

- 순간 CPU 사용률이나 빈 메모리가 많아 보여도 기존 예약을 중복 배정하지 않는다.
- 컨테이너에 기존 자원 한도가 있으면, 해당 컨테이너의 기본 여유와 다른 예약을 고려한 예산도 함께 검사한다.
- 후보는 사용자의 허용 서버와 준비된 본인 컨테이너의 교집합이다. 정상 연결된 노드만 새 배정 후보로 사용한다.
- 예약 검사와 작업 배정 상태 변경을 같은 DB 트랜잭션으로 처리한다. 배정 전송 전에 예약을 확정한다.
- 확정된 대기 정책은 접수 순서로 검토하되 현재 조건을 만족하는 작업부터 배정하는 방식이다. 앞선 작업이 어떤 허용 서버에서도 실행될 수 없으면 대기를 유지하고 다음 작업을 검토한다. 각 배정 직후 남은 예산을 갱신해 다음 작업을 판단한다. 접수 순서가 같을 때는 중앙에서 부여한 단조 증가 순번으로 순서를 정한다.
- 새 요청과 `start_if_available` 요청에도 같은 배정 정책을 적용한다. 먼저 접수되어 현재 실행 가능한 작업을 처리한 뒤 새 요청의 예약 가능 여부를 판단한다. 현재 실행 불가능한 선행 작업을 건너뛰는 것은 허용되지만 실행 가능한 선행 작업의 순서를 빼앗지 않는다.
- 작은 작업의 반복 유입으로 큰 작업이 오래 기다릴 수 있으므로 대기 이유와 시간을 노출한다. 사용자별 순환, 선행 작업을 위한 자원 유보, 실행 중인 작업의 선점은 첫 버전 정책에 포함하지 않는다.
- 허용된 서버와 본인 컨테이너의 유효 최대 예산을 함께 검사한다. 어느 등록 환경에서도 수용할 수 없는 요청은 영구 대기시키지 않고 충족 불가능한 요청으로 설명한다. 등록된 실행환경 자체가 없거나 준비되지 않은 경우는 환경 준비 필요 상태로 별도 안내한다.

이는 협조형 예약이다. 신청량을 초과하거나 MCP·수동 CLI를 거치지 않은 직접 실행은 자동 차단하지 않는다. GPU의 한 장당 작업 하나 규칙도 시스템에 등록된 작업 사이의 예약 정책이며, 미등록 직접 실행의 장치 접근까지 차단하는 보장은 아니다. 미등록 계산이 활발한 서버의 여유 예산을 조정하고, 큰 계산은 공통 도구를 통해 제출하는 운영 규칙을 둔다. NFS I/O 대역폭은 이 CPU·메모리 예약으로 보장하지 않는다.

### GPU 예약과 실행 장치 연결

- 노드 Worker가 GPU 장치별 식별자, 모델, 물리 VRAM 용량, 상태와 컨테이너별 접근 가능한 장치 집합을 보고한다. 컨테이너 내부 GPU 번호가 서로 달라도 같은 물리 장치는 하나의 예약 원장으로 관리한다.
- 작업은 GPU 개수를 요청하고, 필요한 경우 모델·장치별 최소 VRAM을 선택적 조건으로 지정한다. 호스트 메모리 요청과 GPU VRAM 조건을 구분한다. GPU를 사용하지 않는 작업은 GPU 0개로 요청한다.
- 후보 GPU는 허용 서버에 있으며 선택한 개인 컨테이너에서 실제 접근 가능한 장치여야 한다. 개수만 남아 있어도 해당 컨테이너에서 보이지 않거나 조건이 다르면 배정하지 않는다.
- CPU·메모리 예약과 GPU 식별자 할당을 같은 트랜잭션에서 확정한다. 필요한 자원 일부만 선점한 채 나머지를 기다리지 않는다. 한 작업의 GPU들은 같은 실행 서버에서 확보하며 서버 간 분산 GPU 실행은 포함하지 않는다.
- NVIDIA CUDA 실행에서는 이미 컨테이너에 노출된 장치 중 예약된 UUID를 실행 래퍼의 `CUDA_VISIBLE_DEVICES` 등에 연결하고, 프로그램이 사용하는 장치 인자도 맞춘다. CPU 전용 작업에는 GPU를 선택하지 않도록 설정한다. 이는 협조적 장치 선택이며 보안 격리나 GPU 메모리 강제 제한이 아니다. 다른 GPU 런타임은 실제 환경에 맞는 장치 선택 방법을 확인해야 한다.
- 이미 실행 중인 개인 컨테이너에 새로운 GPU 장치를 환경변수만으로 추가할 수 있다고 가정하지 않는다. 작업에 필요한 장치가 노출되지 않은 환경은 준비가 필요함을 안내하며 시스템이 컨테이너를 임의로 재생성하지 않는다.
- Worker는 실제 실행 직전에도 작업이 참조하는 등록 버전·컨테이너 ID·실행 UID와 예약 GPU 접근 가능 집합을 재검사한다. 검토 이후 대상이 바뀌었다면 다른 컨테이너나 GPU로 임의 실행하지 않고 준비 상태 변경을 보고한다.
- 컨테이너를 재생성하거나 GPU 장치 구성이 바뀌면 등록 정보를 다시 확인한다. 완료·실패·취소로 실제 종료와 정리를 확인한 뒤 GPU 예약도 함께 반환한다. `UNKNOWN` 상태는 GPU 예약을 유지한다.

## 자원 축소 제안과 사용자 선택

검토와 실제 제출을 분리한다. 검토 단계에서는 작업을 실행하거나 대기열에 등록하거나 자원을 선점하지 않는다.

아래는 에이전트의 사용자 대화 예시다. 수동 CLI도 같은 검토·제출 API와 승인 조건을 적용하며, 선택 절차는 위의 수동 도구 터미널 동작을 따른다.

1. 에이전트가 원래 실행안과 실제로 실행 가능한 대안들을 준비한다.
2. `plan_job`이 권한·환경·예약 현황을 확인해 원래 안의 배정 가능 여부, 대기 이유, 실행 가능한 대안을 반환한다.
3. 에이전트가 예를 들어 “16 threads / 64 GiB는 현재 대기가 필요합니다. B 서버에서 8 threads / 64 GiB는 현재 예약 가능합니다. 원래 조건으로 기다릴까요, 8 threads로 실행할까요?”라고 설명한다. 시작 시점이나 실행 시간을 근거 없이 보장하지 않는다.
4. 원래 조건으로 대기 선택: `submit_job`을 `queue_if_unavailable` 모드로 호출한다. 접수 뒤 조건이 충족되면 상주 서비스가 자동 실행한다.
5. 축소 실행 선택: 선택된 명령과 자원량으로 `submit_job`을 `start_if_available` 모드로 호출한다. 중앙 서비스가 현황과 권한을 다시 검사하고, 먼저 접수된 실행 가능한 작업을 고려한 뒤 원자적으로 예약한다.
6. 선택하는 동안 자원이 소진되었다면 `start_if_available`은 작업을 새로 대기 등록하지 않고 상황 변경을 반환한다. 에이전트가 다시 설명하며 무단으로 추가 축소하거나 다른 조건으로 제출하지 않는다.

각 실행안은 자원량뿐 아니라 그 자원량에 맞는 명령 인자와 환경 설정을 포함한다. 16에서 8 threads로 줄이면 프로그램의 threads 옵션과 필요한 스레드 환경변수도 맞춘다. 예약 숫자만 바꾸지 않는다.

메모리를 줄여도 실행 가능한지는 중앙 서비스가 추측할 수 없다. 프로그램 옵션, 확인된 실행 이력, 사용자 확인 등 근거가 있는 대안만 제안한다. 근거가 없으면 메모리는 유지하고 CPU 축소만 검토하거나 원래 요청을 대기시킨다. CPU 축소도 프로그램이 해당 병렬도를 지원할 때만 제안한다.

GPU 장수 축소나 CPU 실행으로의 전환도 프로그램이 지원하고 사용자가 해당 대안을 선택한 경우에만 허용한다. GPU 요청이 충족되지 않는다고 임의로 GPU 없이 실행하지 않는다.

검토 결과는 그 시점의 정보이다. 최종 제출의 선택된 실행안 전체를 검증하고 저장한다. 재시도 키는 사용자 단위로 관리하고, 같은 키에 다른 실행안이 오면 오류를 반환한다. 동일 요청의 통신 재시도는 기존 작업 ID를 돌려준다.

## 작업 수명과 완료 보고

```text
QUEUED → DISPATCHING → RUNNING → SUCCEEDED / FAILED / CANCELLED
                       ↘ UNKNOWN → 상태 대조 후 확정
```

`DISPATCHING`도 연결 오류나 실행 여부 불명확 시 `UNKNOWN`이 될 수 있다. `UNKNOWN`은 종료 상태가 아니며 예약을 유지한다. 대기 취소는 즉시 가능하지만 실행 중인 작업의 예약은 실제 종료와 정리 확인 뒤 반환한다.

- 중앙 DB에 작업 ID, 사용자, 승인된 실행안, 배정 노드·컨테이너, 실행 식별자, 예약, 상태, 결과 위치를 영속 저장한다.
- 제출한 진입 스크립트는 작업별 사본과 해시로 고정한다. 이 스크립트가 참조하는 다른 코드·설정·데이터까지 고정되는 것은 아니다. 실행환경은 등록 프로필과 식별자를 기록한다. 데이터 전체나 개인 컨테이너 전체의 스냅샷은 범위 밖이다.
- Worker는 시작 요청을 로컬에 기록하고 작업·실행 식별자로 중복 요청을 구분한다. 실행 여부를 확정할 수 없는 재시작 구간에서는 임의로 다시 시작하지 않고 `UNKNOWN`으로 보류한다.
- 실행 래퍼는 작업 전용 프로세스 그룹을 사용한다. 명령은 필요한 하위 프로세스를 기다려야 하며, 스스로 분리되어 백그라운드 서비스가 되는 작업은 초기 지원 범위 밖이다. 완료·취소 시 다른 개인 세션에 영향을 주지 않고 해당 작업 프로세스의 종료를 확인한다.
- 취소와 시작 요청의 순서가 뒤바뀌어도 안전하도록 Worker는 실행 식별자별 취소를 영속 기록한다. 취소된 식별자로 늦게 도착한 시작 요청은 재시작 후에도 거절한다. 시작·취소 판정은 Worker 내부에서 직렬화하며, 이미 시작됐다면 해당 작업을 종료·정리한다. 취소된 작업이 나중에 실행될 가능성과 현재 실행이 모두 제거되었음을 확인한 뒤 예약을 반환한다.
- 정상 종료는 종료코드와 결과 위치를 기록한 직후 중앙에 보고한다. 중앙은 상태 확정과 예약 반환을 한 번만 처리하고 곧바로 배정 루프를 깨운다.
- 보고 실패 시 Worker가 영속 보관한 완료 이벤트를 재전송한다. 중앙은 작업·실행 식별자로 중복 완료를 무시한다.
- Docker 실행·컨테이너 종료 이벤트를 보조적으로 사용하되, 이벤트 유실에 대비해 재연결·재시작 시 실제 실행 상태와 로컬 기록을 대조한다. 이 점검도 코드가 수행하며 LLM은 기다리지 않는다.
- Worker 연결이 끊긴 노드는 새 배정에서 제외한다. 시간 초과만으로 성공 처리하거나 실행 여부가 불명확한 작업을 다른 서버에서 재실행하지 않는다.
- 자동 대조로 해결되지 않는 `UNKNOWN`은 운영자가 작업·실행 식별자, 컨테이너 ID, 실행 기록과 종료 증거를 확인한다. 노드 복구 또는 실행 중단을 확인하기 전에는 예약을 강제로 반환하지 않는다. 확인 근거와 처리 결과를 기록하는 수동 복구 절차를 운영 문서에 포함한다.
- 완료 감지부터 다음 배정까지 지연을 시험에서 측정한다. 정확히 0초인 실행 전환은 약속하지 않는다.

## 사용자별 Discord 시작·종료 알림

사용자가 지정한 수신 방식은 동일한 Discord 서버 안의 사용자별 채널이다. 예를 들어 연구실 Discord 서버에 사용자 A용 채널과 사용자 B용 채널을 두고 각각의 채널 Webhook을 연결한다. 채널과 Webhook은 Discord에서 먼저 준비하고 시스템에는 본인의 목적지를 등록한다. 첫 버전에서 채널 자동 생성, DM 봇, 공용 채널 전체 멘션은 구현하지 않는다. 사용자가 채널 연결을 설정한 뒤에는 해당 사용자의 각 작업 시작·종료 알림을 추가 승인 없이 자동 전송한다.

### 기존 알림과의 관계

현장에서 확인한 `/10Gdata/ezy/05_Toy_Projects/discord/notify_run.sh`는 실제 명령이 끝난 뒤 종료코드와 실행 시간 등을 `discord_notify.py`로 보내며, 알림 실패가 원래 명령의 종료코드를 바꾸지 않도록 되어 있다. 기존 메시지 형식과 Webhook 기반 전송 방식은 참고하되, 사용자별 라우팅·시작 이벤트·영속 재전송은 새 hub에 구현한다. 기존 `.env`는 존재와 읽기 가능 여부만 확인했으며 값은 읽거나 출력하지 않았다. 현재 Webhook의 유효성이나 실제 전달 성공은 검증하지 않았다.

기존 개인 알림 스크립트는 수정하지 않는다. hub가 관리하는 작업의 알림은 hub가 한 경로에서 담당하도록 공통 스킬에 명시한다. 동일 작업에 기존 알림 래퍼를 추가 적용해 중복 전송하지 않는다. 이미 알림 호출이 들어 있는 사용자 스크립트는 임의 편집하지 않고 연결 시험 시 중복 경로를 확인한다.

| 성공 종료 | 작업과 필요한 하위 프로세스의 종료·정리 및 성공 종료코드 확인 | 작업 ID·표시 이름, 실행 위치, 실행 시간, 종료코드, 결과·로그 경로 |
| 실패 종료 | 실행 실패 또는 비정상 종료를 확인 | 작업 ID·표시 이름, 실행 위치, 확인된 오류 분류·종료코드, 로그 경로 |
| 취소 완료 | 취소 요청 이후 실제 실행 중단·정리 확인 또는 대기 작업 취소 확정 | 작업 ID·표시 이름, 취소 결과, 실행됐던 경우 실행 시간과 로그 경로 |

접수나 예약만으로 시작 알림을 보내지 않는다. 실행 전에 취소되거나 시작에 실패한 작업에 시작 알림을 만들지 않는다. 연결이 끊겨 `UNKNOWN`이 된 상태를 정상 종료·실패 확정으로 통보하지 않는다. 주기적 진행 알림과 대기 중 반복 알림은 기본 범위 밖이다.

알림에는 허용된 요약 필드만 넣으며 전체 명령줄, 환경변수, 원본 로그 내용, 비밀 URL을 자동 첨부하지 않는다. 표시 이름은 작업 이름을 사용하고 원본 명령을 이름으로 자동 복사하지 않는다. Webhook 메시지의 자동 멘션은 끈다. 로그는 내용을 전송하는 대신 등록된 작업의 로그 경로를 안내한다.

### 사용자별 채널과 비밀정보

- 인증된 사용자 ID를 알림 목적지에 연결한다. 작업 제출자가 임의로 다른 사람의 수신 목적지를 지정하지 못하게 한다.
- 설정 시 Webhook이 연구실의 지정 Discord 서버와 등록할 사용자 채널에 연결되는지 확인한다. 채널의 실제 읽기 권한은 Discord 설정으로 관리하며 사용자별 채널을 비공개로 운영하려면 해당 사용자와 운영자만 볼 수 있게 준비한다.
- Webhook URL은 메시지 전송 자격증명으로 취급한다. CLI의 숨김 입력이나 보호된 설정 경로를 통해 등록하고, 중앙의 접근이 제한된 비밀 저장소에 둔다. MCP·작업 DB에는 참조 ID와 비밀이 아닌 채널 식별자·설정 상태만 저장한다. 사용자 입력을 임의 파일 경로로 사용해 비밀 파일을 읽지 않는다.
- 설정 조회·감사 로그·오류 응답에 Webhook 원문을 반환하지 않는다. 현재 사용자의 개인 Webhook을 다른 연구원에게 공용으로 적용하지 않는다.
- 알림 목적지가 전혀 등록되지 않은 사용자의 작업 제출은 예약·대기 등록 전에 `NOTIFICATION_NOT_CONFIGURED`로 거절하고 초기 연결 설정을 안내한다. 설정 완료 후 다시 제출할 수 있으며 알림 없이 접수된 것으로 오해하게 하지 않는다. 등록된 알림 목적지의 전송 장애는 실행 중인 계산의 결과를 바꾸거나 작업을 재실행하는 이유가 되지 않는다.

### 전송과 복구

1. 중앙은 확인된 작업 시작·종료 상태와 해당 알림 전송 대기 기록을 같은 DB 트랜잭션으로 저장한다. 작업 ID·실행 식별자·이벤트 종류·목적지 설정 버전으로 중복 생성을 방지한다. 아직 실행 식별자가 없는 대기 취소·시작 전 실패 이벤트는 작업 ID와 명시적인 미실행 구분값을 사용해 식별한다. 이후 작업 예약 반환과 다음 배정은 Discord 성공 여부와 독립적으로 진행한다.
2. 실제 프로세스 시작·종료 관측은 Worker가 발생 순서와 시각을 붙여 영속 기록한다. 시작 보고도 완료 보고와 동일하게 중앙의 접수 확인까지 보관·재전송하며, 중앙 장애 후 재연결되면 아직 실행 중인 작업의 시작 이력도 복구한다. 빠르게 끝난 작업이나 역순으로 도착한 보고도 검증된 이력에 따라 시작·종료 알림을 구성하고, 늦게 온 시작 보고가 종료 상태를 실행 중으로 되돌리지 않게 한다. 시작 사실이 확인되지 않았으면 시작 알림을 추정해 만들지 않는다.
3. 알림 전송 루프는 사용자별 목적지를 조회하고 전송한다. 목적지 설정 버전은 작업 접수 시 연결해 실행 전 취소에도 사용하며, 중간 설정 변경으로 기존 알림이 다른 사용자의 채널로 이동하지 않게 한다. 유출·폐기 등으로 설정을 비활성화한 경우 그 버전의 미전송 알림은 보류하고 명시적으로 연결을 복구한다.
4. Discord Webhook은 전송 확인 응답을 받는 모드를 사용해 성공 시 메시지 ID와 전송 시각을 기록한다. HTTP 429는 `Retry-After` 또는 `retry_after`를 따르고, 일시적 네트워크·서버 오류는 간격을 늘려 재시도한다. 잘못된 목적지·권한 등 영구 오류는 별도 실패 상태로 남겨 `job_status`와 설정 상태에 표시한다.
5. 같은 실행의 알림은 가능한 한 발생 순서로 전송한다. 시작 알림의 장기 장애 때문에 종료 결과까지 무기한 숨기지 않도록, 종료 알림에 실제 시작·종료 시각을 함께 담아 전달할 수 있게 한다. 이미 종료 결과가 전달된 뒤 늦은 시작 알림만 새로 보내는 것은 생략하거나 종료 결과에 병합한다.
6. 내부 이벤트와 전송 대기 기록은 중복을 제거한다. 다만 Discord가 메시지를 수신한 뒤 응답이 유실되면 재전송 시 외부 메시지가 중복될 수 있다. 작업·실행·이벤트 식별자를 알림에 포함해 구분하며 외부 전송의 정확히 한 번 보장을 약속하지 않는다. 알림 재전송 때문에 계산을 다시 실행하지 않는다.

Discord 장애나 전송 지연은 알림 상태에만 영향을 준다. 계산 결과, 예약 반환, 다음 작업 배정은 정상적으로 진행하며 재시작 후 미전송 기록을 복구한다.

현재 허브 구현은 `src/cowork_hub/`의 `models.py`, `store.py`, `service.py`, `api.py`, `notifications.py`, `cli.py`와 모의 실행용 `demo.py`로 구성했다. 조회·검토 MCP는 `mcp_server.py`의 사용자용 HTTP 클라이언트와 stdio 도구로 구현했다. 현재 `cowork-hub` CLI는 관리자 초기화·허브 실행·데모용이며 사용자 제출 명령이 아니다. 후속 수동 CLI는 `cowork-run`과 `cowork`를 제공하고, MCP 어댑터와 동일한 HTTP 클라이언트·실행안 형식을 사용한다. 웹은 같은 API의 현황·관리 기능을 사용한다. 중앙 정책·예약은 `service.py`에 함께 두었으며 검증은 `tests/`에 둔다. 실제 SSH 증명·Worker·runner·GPU 실행 매핑·수동 CLI·작업 제출 MCP·공통 스킬·웹 화면과 관리 API 확장은 이후 단계에서 추가한다. Worker 계약은 `docs/worker-contract.md`에 정리했다. 외부 큐 시스템은 필요가 입증되기 전 추가하지 않는다.

## 구현 순서

현재 우선순위는 **실제 MCP 연결 → 사용자 권한 조회 → Worker 연결과 시험 계산 → 웹 관리**다.
조회·검토 MCP를 구현했고, 개인 토큰으로 실제 사용자 조회까지 확인했다. 설치와 검증 범위는
`docs/mcp-setup.md`를 따른다. 사용자 기준 UID·GID 저장·중복 검사·환경 대조는 코드 검증을 마쳤으며,
운영 허브 배포·ezy 기준값 설정·226 로컬 실행 시험까지 완료했다. 첫 대상 컨테이너의 현재 상태는 `docs/worker-226-setup.md`를 따른다. 웹을 위한 전체 관리 API 확장은 후속으로 둔다.

1. **실제 환경 확인:** 서버 OS·Docker 방식, CPU·메모리·GPU 장치와 드라이버, 사용자별 허용 서버, 준비된 컨테이너·UID/GID·경로·GPU 노출, 실제 SSH 접속 형식, 대표 배치 명령, 기존 실행 작업을 조사한다. 운영 작업을 건드리지 않고 시험 예산·컨테이너를 정한다.
2. **중앙 예약 로직:** 인증 주체, 정책, 실행안, 영속 작업 상태, CPU·메모리·GPU의 원자적 예약, 검토·제출 모드, 중복 방지를 구현하고 가짜 Worker로 검증한다.
3. **MCP 첫 연결과 실제 환경 검증:** 조회·검토 MCP를 개인 컨테이너의 에이전트에 등록하고 실제 사용자 권한 조회를 확인한다. UID/GID 규칙 검사와 SSH 경로를 통한 개인 환경 등록을 구현하고 허용 서버·실제 컨테이너·사용자 대응을 검증한다. 시험용 개인 컨테이너에 Worker·래퍼를 연결한 뒤 제출·취소 MCP를 추가해 시험 계산을 확인한다. GPU 장치 매핑, 로그, 정상·실패 종료, 작업 단위 취소, 완료 재전송, 상태 대조를 검증한다.
4. **수동 제출 CLI:** `cowork-run`과 에이전트 없는 설정·환경 등록·조회·취소 도구를 구현한다. 작업별 작업 경로를 허브·Worker까지 연결하고 인자 보존, 제출 재시도, 대기 조회·분리, 원격 종료코드, 실패 시 로컬 우회 실행 방지를 검증한다. 이 단계에서 에이전트 없이 실제 명령 한 건의 전체 경로를 시험한다.
5. **스킬·알림:** 검토 → 사용자 선택 → 제출 절차와 실제 threads 인자 변경을 공통 스킬로 작성한다. 수동·MCP 작업 모두 기존 허브의 알림 경로를 이용한다. 사용자별 Discord 채널 설정과 비동기 알림 전송을 모의 전송 대상으로 먼저 검증하고, 실제 전송은 등록된 사용자 채널을 대상으로 별도로 확인한다.
6. **두 노드 통합 시험:** 서로 다른 허용 서버 목록을 가진 두 사용자가 수동 CLI와 MCP로 제출하며 배정·대기·완료 연쇄와 장애 시나리오를 확인한다. 통과 후 Worker 연결 대상 서버를 확대한다.
7. **웹 현황·설정 관리:** 관리자 조회 API와 브라우저 로그인·역할 검사를 준비하고 서버·대기열·본인 작업 현황부터 연결한다. SSH 접속 환경 등록, 사용자별 허용 서버 설정과 개인 MCP 토큰 발급·폐기를 연결하고, 예산 변경·배정 중지와 알림 설정을 추가한다. 실제 사용자 권한과 동일한 작업·예약 원장을 사용하는지 검증한다.

## 완료 기준과 검증

- 다른 허브 사용자에게 같은 기준 UID를 등록하면 거절하고, 공동 그룹을 위한 동일 GID 등록은 허용한다.
- 환경의 UID 또는 기본 GID가 사용자 기준값과 다르거나 기준값이 미설정이면 활성화하지 않는다. 값이 일치해도 소유권 검증 실패·금지 서버 등록은 거절한다.
- 기존 DB에 기준값 저장 기능을 추가해도 사용자·환경·작업·예약이 보존된다. 기준값 변경은 관련 환경의 재검증을 요구하며, 실행 중인 작업의 식별자나 예약을 바꾸지 않는다.
- 웹 일반 사용자가 관리자 API나 다른 사용자의 상세 작업·로그에 접근할 수 없는지 검증한다. 관리자 화면의 설정 변경도 API 권한 검사·감사 기록을 거친다.
- 웹에서 발급한 토큰은 본인의 기존 권한만 가지며, 타인의 토큰 관리나 역할 승격은 거절된다. 새 토큰 발급 후 기존 토큰도 유지되고, 개별 폐기 후에는 해당 토큰의 이후 인증만 거절되는지 확인한다. 토큰 목록·로그에는 원문이 노출되지 않으며 폐기로 기존 작업·예약이 바뀌지 않는다.
- 웹·CLI·MCP에서 같은 작업·예약·대기 순서를 조회하며, 웹을 닫아도 배정·완료·알림이 진행된다. 갱신 실패 시 마지막 성공 시각과 연결 상태를 표시한다.
- 웹의 예약 수치와 실제 사용량을 혼동하지 않으며, Worker 미연결·컨테이너 미검증·`UNKNOWN`을 실행 가능이나 종료로 오표시하지 않는다.
- 예산 변경과 작업 배정이 동시에 일어나도 초과 예약이 발생하지 않는다. 예약 이하 예산 축소는 거절하고, 새 배정 중지는 실행 중인 작업과 완료 보고를 방해하지 않는다.
- 웹에서 SSH 경로를 추가해도 허용 서버 권한이 늘어나지 않으며 검증 전에는 배정되지 않는다. 사용자 권한 변경은 새 제출·배정에 적용하고 실행 중인 작업의 예약을 조기 반환하지 않는다.
- 로그인 만료·권한 회수·위조 요청에서 웹 설정 변경이 거절된다. 공용 관리자·Worker 토큰이 웹 코드나 브라우저 저장소에 포함되지 않는다.
- 수동 CLI와 MCP가 동시에 제출한 작업들이 하나의 자원 원장과 접수 순서를 공유한다. 제출 경로에 따른 우선권·별도 예약·별도 알림이 없다.
- 에이전트 없이 사용자 설정·환경 등록·명령 제출·조회·취소를 수행할 수 있다. 금지 서버·다른 사용자의 환경·잘못된 인증은 수동 CLI에서도 거절된다.
- 접두 도구가 공백·따옴표·상대 인자와 제출 당시 작업 경로를 보존한다. 다른 후보 컨테이너의 경로·프로그램 부재를 숨기거나 임의 복사·로컬 실행으로 우회하지 않는다. 파이프라인은 스크립트 단위로 검증한다.
- 수동 CLI 접수 후 터미널·SSH를 닫아도 대기 작업이 자원 반환 뒤 실행되고 시작·종료 알림을 받는다. 완료 조회는 원격 종료코드를 반영하고, 분리 모드의 접수 성공과 계산 성공을 구분한다.
- 수동 CLI 응답 유실·재시작 후 같은 요청 키로 확인해도 작업은 하나다. 인증·접속·초기 설정 오류 시 원래 명령이 예약 없이 실행되지 않는다.
- 입력을 받을 수 없는 CLI 실행은 질문을 기다리며 멈추지 않는다. 자원·명령의 축소는 준비된 실행안을 명시적으로 선택했을 때만 수행한다.
- 모의 Discord 전송 대상으로 실제 시작 이후 시작 알림이 생성되고, 성공·실패·취소 종료를 구별하는지 검증한다. 접수만 한 작업과 실행 전 취소된 작업에 시작 알림이 없는지 확인한다.
- 같은 Discord 서버의 사용자별 채널 연결을 검증하고, 사용자 A의 작업이 B의 채널로 전달되지 않는지 확인한다. 설정 조회·오류·로그·MCP 출력에 Webhook 값이 노출되지 않는지 검증한다.
- 미등록 목적지로 제출하면 작업·예약이 생성되지 않고 설정 필요가 반환되는지 확인한다. 설정 후 재제출은 접수되며, 이후 알림 전송 장애가 계산을 중단하지 않는지 확인한다. 대기 취소는 취소 종료 알림만, 시작 전 실패는 실패 알림만 생성되는지 확인한다.
- 중앙 장애 중 시작한 작업의 시작 이력이 재연결 후 복구되어 시작 알림이 생성되는지 확인한다.
- 중복 Worker 보고와 hub 재시작에도 같은 이벤트의 전송 대기 기록은 하나인지 확인한다. 아주 짧은 작업, 종료 보고 선도착, 전송 중 응답 유실도 시험하고 외부 중복 가능성을 정확히 보고한다.
- HTTP 429·일시적 실패·영구 오류를 모의 응답으로 시험한다. 전송 지연 중에도 자원이 반환되고 다음 작업이 시작되며 계산 결과가 바뀌지 않는지 확인한다. 중도 목적지 변경·비활성화와 종료 알림보다 늦어진 시작 알림도 검증한다.
- 사용자가 새 개인 컨테이너의 SSH 경로를 제출하면 접속·실제 서버·컨테이너·사용자 대응을 확인한 뒤 본인의 실행환경으로 등록된다. 금지 서버 경로, 만료·재사용 검증값, 서버 이름 위조, 다른 사용자의 기존 환경 등록은 거절된다.
- 동일한 컨테이너를 여러 SSH 별칭으로 등록해도 서버·컨테이너 자원이 중복 생성되지 않는다. 컨테이너 이름 재사용이나 다른 ID로의 교체는 재검증 전 배정하지 않는다. 등록 실패나 네트워크 단절 상태의 환경에는 작업을 배정하지 않는다.
- 서로 다른 컨테이너에서 같은 물리 GPU가 다른 번호로 보이더라도 동일 장치를 두 작업에 중복 예약하지 않는다. 두 작업이 한 장을 요청하면 하나는 실행하고 다른 하나는 대기하며, 종료 후 다음 작업에 같은 장치를 예약할 수 있다.
- CPU·메모리·GPU를 동시에 충족하지 못하면 일부만 예약하지 않는다. 접근 불가능한 GPU, 모델·VRAM 조건 불일치, GPU 미노출 컨테이너는 GPU 작업 후보에서 제외된다.
- 공유 NFS에 동일한 등록 검증값이 보이는 복수 컨테이너를 시험해 실제 SSH 접속 컨테이너와 실행 UID가 정확히 확인되는지 검증한다. 등록·검토 이후 실행 직전 컨테이너 ID나 GPU 접근 집합이 바뀌면 실행이 거절되는지 확인한다.
- Worker 단절과 중복 완료 보고에서도 `UNKNOWN`의 GPU UUID 예약이 유지되고 확인 후 한 번만 반환되는지 검증한다. 최초 SSH 세션 종료는 등록 환경의 실행 가능 상태를 바꾸지 않는지 확인한다.
- 두 GPU가 노출된 시험 환경에서 예약한 UUID가 실제 CUDA 장치 선택에 반영되는지 확인한다. 장치 노출 설정과 작업별 선택을 구분해 검증하며 환경변수만으로 강제 격리된다고 보고하지 않는다.
- A·B 허용 사용자는 C에 배정되지 않는다. 직접 C를 지정하거나 다른 사용자를 사칭하거나 남의 작업을 취소하려는 요청도 거절된다.
- B를 공유하는 사용자들이 동시에 제출해도 모든 예약 합계가 설정 예산을 넘지 않는다. 컨테이너별 예산이 있으면 그것도 지킨다.
- 선행 작업의 요청량이 현재 여유보다 크면 대기를 유지하고, 뒤의 작은 작업은 조건에 맞는 서버에서 실행된다. 둘 다 실행 가능하고 동시에 수용할 자원이 부족하면 먼저 접수된 작업이 우선된다. 신규·축소 즉시 실행 요청도 이 순서를 지킨다.
- 검토만으로 실행·대기 등록·예약이 생기지 않는다. 사용자가 대기를 선택하면 원래 실행안을 유지한다.
- 축소안 선택 시 실제 명령의 threads 값과 예약 CPU가 일치한다. 근거 없는 메모리 축소안은 제시하지 않는다.
- 검토 뒤 가용 자원이 바뀌어도 초과 예약이 발생하지 않는다. 즉시 실행 선택이 실패하면 새 작업을 몰래 대기열에 넣지 않는다.
- 제출 응답이 유실되어 같은 키로 재요청해도 작업은 하나다. 같은 키에 다른 내용은 거절한다.
- 작업 1 실행, 작업 2 대기 상태에서 에이전트·MCP·수동 CLI 연결과 사용자 SSH를 닫아도 작업 1 종료 후 작업 2가 자동 실행된다.
- 명령 실패·취소·컨테이너 종료에서도 상태와 예약이 실제 실행 상황에 맞게 정리된다. 정상 종료와 일반적인 오류 종료를 구별한다.
- 완료 보고 유실·중복, 중앙 재시작, Worker 재시작, 네트워크 단절을 시험한다. 알 수 없는 실행을 중복 실행하거나 자원을 조기 반환하지 않는다.
- 취소와 시작 메시지의 순서를 뒤집고 취소 기록 후 Worker를 재시작해도 늦게 도착한 시작 요청이 실행되지 않는다. 취소와 완료가 경합해도 예약은 한 번만 반환된다.
- 시험용 작업 이외의 기존 개인 컨테이너 세션이 취소·종료 처리에 영향받지 않는다.

- 실행 단위 확정 반영: 사용자의 명령·스크립트 단위 선택을 가정에서 확정 요구사항으로 옮기고, 전체 실행 동안의 예약 유지와 내부 동시 실행의 합산 기준을 명시했다.
- 대기 정책 확정 반영: 사용자가 선택한 접수 순서 중 실행 가능한 작업부터 배정하는 방식을 명시했다. 신규·축소 요청도 같은 순서를 적용하도록 일관성을 확인하고, 선행 작업 건너뛰기와 실행 가능한 작업 간 우선순위 검증 항목을 추가했다.
- 컨테이너 준비 범위 확정 반영: 미리 준비해 등록한 개인 컨테이너만 사용하도록 확정했다. 서버 접근 권한과 실행환경 준비 상태를 모두 만족해야 배정할 수 있음을 명시했다.

- GPU·자가 등록 확장 검토: 별도 독립 에이전트 검토를 완료했다. 필수 수정 지적은 없었으며, 선택적 GPU 조건, 최초 SSH 세션과 준비 상태의 분리, 등록 버전, 공유 NFS에서의 검증값 혼동 방지, 실행 직전 대상 재검사, GPU 장애 복구 검증을 추가 반영했다. 구체적인 SSH 확인 절차와 GPU 실행 매핑은 실제 환경 조사·구현으로 검증해야 한다.

- Discord 알림 확장 검토: 별도 독립 에이전트 검토를 완료했으며 필수 수정 지적은 없었다. 작업 접수 시 목적지 버전 고정, 미실행 이벤트 식별, 목적지 미등록 제출의 명확한 처리, 시작 보고 재전송, 설정 후 자동 전송 및 관련 검증 항목을 보완했다. 기존 알림 코드의 읽기 확인과 문서 검토만 수행했고 실제 Discord 메시지는 보내지 않았다.

- 수동 사용자 지원 반영: `cowork-run` 접두 제출 방식과 공통 허브·Worker 경로, 사용자 설정·관리, 인자·작업 경로 보존, 종료 조회·분리·취소, 재시도, 축소안 선택과 혼합 제출 검증을 추가했다. 주 에이전트가 기존 예약·알림 정책과 문서 일관성을 확인했다. 이번 변경은 계획·계약 문서 수정이며 수동 CLI를 구현했다는 의미는 아니다.

- 웹 플랫폼 요구 반영: 웹 대시보드 제외 문구를 제거하고 공통 API를 사용하는 역할별 현황·관리 화면, 관리 API 확장, 예약 수치의 의미, 안전한 예산 변경·배정 중지·취소, 로그인·감사 기록과 통합 검증을 추가했다. 네 서버 등록 완료 상태도 반영했다. 이번 변경은 계획 문서 수정이며 웹 구현이나 배포를 수행했다는 의미는 아니다.
